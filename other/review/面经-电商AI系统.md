# 电商AI系统项目面经

## 1. 项目简介

该项目是一个基于 Go 和 go-zero 的电商微服务系统，覆盖用户、商品、库存、购物车、结算、优惠券、订单、支付、审计等核心后端链路，并在此基础上新增 AI 智能客服能力。AI 侧使用 Eino 构建多 Agent 编排，通过 SSE 对外流式响应，通过工具调用安全访问真实电商 RPC，并围绕高风险操作确认、上下文记忆、RAG 检索和审计记录做工程治理。

## 2. 简历 bullet

- **微服务交易一致性：** 针对下单链路跨结算、优惠券、订单等多个服务，单库事务无法覆盖跨服务失败的问题，将创建订单入口设计为 Saga 编排：先锁定优惠券和结算状态，再创建订单，失败时走对应补偿接口；服务内部仍用本地事务保证各自状态原子更新，最终能用订单、结算、优惠券和补偿日志验证链路一致性，真实吞吐和 P99 延迟仍需通过压测补充。
- **库存资源可靠治理：** 针对并发下单、重复结算可能导致库存重复扣减或资源滞留的问题，引入预扣库存和请求指纹机制：结算服务用 Redis 记录短期幂等 key，库存服务用 Lua 脚本原子完成幂等检查、库存校验、扣减和预扣标记，并配合超时扫描释放预占资源；该方案的结果可通过库存 key、预订单状态和超时释放消费记录验证。
- **可靠事件投递：** 针对订单取消、超时关闭、支付成功等跨服务后置动作容易受下游波动影响的问题，引入 Outbox + Kafka 的事件投递机制：核心业务状态和待投递事件在同一事务内写入，后台 dispatcher 认领待发送消息并按退避策略重试，下游消费者独立释放库存、优惠券和结算资源；线上收益未量化，但架构上将主交易状态与异步资源释放解耦。
- **安全工具编排：** 针对大模型 tool call 不可信、可能伪造身份或把失败包装成成功的问题，将电商业务能力注册为统一工具目录，并在执行层集中做 schema 校验、可信用户身份注入、超时控制、错误分类、有限重试、敏感参数脱敏和工具调用审计；查询工具和写工具采用不同重试边界，失败统一返回结构化结果，避免模型绕过业务安全边界。
- **高风险操作确认：** 针对 AI 发起下单、取消订单、删除购物车等动作需要用户二次确认的问题，设计确认状态机和中断续跑机制：高风险工具先创建确认记录并中断，确认后通过 checkpoint 恢复原工具调用，Redis 短锁合并并发确认，MySQL 条件更新作为最终状态来源；重复、过期、跨用户确认都会被拒绝，避免一次确认被多次执行。
- **上下文与记忆治理：** 针对多轮对话无限注入历史导致 token 膨胀、工具事实丢失和提示注入风险的问题，将原始消息、摘要、近期窗口、工具事实、用户画像和长期事件分层管理；模型调用前由中间件临时组装上下文，摘要和画像失败时降级到近期消息，记忆不能覆盖 system prompt、工具白名单和确认策略，从架构上保留安全规则优先级。

## 3. 面试问题

### 主题一：整体架构与服务拆分

#### 1. 你这个项目整体是怎么拆服务的？为什么这么拆？

口播版：我这个项目主体是一个 Go 语言的电商微服务系统，整体用 go-zero 做 API 和 RPC 分层。基础业务拆成用户、认证、商品、库存、购物车、结算、优惠券、订单、支付和审计服务，每个服务维护自己的配置、RPC 契约和数据模型。这样拆不是为了炫技，而是因为电商交易链路天然有不同的一致性边界，例如库存扣减、优惠券锁定、订单状态和支付状态的生命周期都不一样。后来我在这个基础上新增了 AI 客服能力，但没有让 AI 直接侵入原有业务服务，而是新增 `apis/ai` 作为 SSE 网关，`services/aiagent` 作为编排层。这样原业务 RPC 仍然是事实来源，AI 只是一层受控的自然语言入口，方便单独做安全、确认、审计和上下文治理。

追问 1：如果服务拆太细，会不会增加复杂度？

口播版：会，所以我在这个项目里不是按数据库表机械拆服务，而是按业务一致性边界拆。比如商品查询和推荐属于商品域，库存预扣属于库存域，结算单负责商品快照、金额和预订单状态，订单服务负责最终订单状态，支付服务负责支付单和回调。拆分后确实会带来服务发现、配置、链路追踪、事务补偿和测试成本，所以项目里通过 go-zero RPC、Consul、统一配置和公共错误码降低接入成本。我的理解是，服务拆分要能回答“这个服务为什么能独立演进”，如果只是把函数拆成服务，复杂度会大于收益。

追问 2：AI 客服为什么不直接写进订单或用户服务里？

口播版：我没有把 AI 写进订单或用户服务，主要是为了隔离不确定性。AI 服务会依赖大模型、工具调用、流式事件、上下文、确认状态和 RAG，这些能力的变化频率和传统电商 RPC 不一样。如果把它塞进订单服务，订单服务就会同时承担交易一致性和模型编排两类职责，风险很高。现在的设计是 AI 编排层通过工具调用访问订单、库存、优惠券等 RPC，业务服务不用理解 Eino 类型，也不会信任模型参数。这样 AI 出问题时，可以降级为“稍后重试”，不会污染原有下单、支付、库存这些核心链路。

#### 2. API 层和 RPC 层分别承担什么职责？

口播版：API 层主要面向客户端协议，负责 HTTP 路由、鉴权、中间件、参数转换和响应格式。RPC 层主要面向内部业务能力，负责核心业务逻辑、本地事务、状态机和数据访问。比如订单创建的外部 API 会从登录态拿用户 ID，然后发起 Saga 编排；真正订单记录的创建在订单 RPC 内部完成。AI 也是类似，`apis/ai` 负责接收 POST JSON、设置 SSE 响应头、心跳、超时和事件转发；`services/aiagent` 负责会话准备、幂等、RAG、Agent 编排、工具执行和消息持久化。这样协议层和业务层分开后，前端协议变化不会直接冲击核心业务实现。

追问 1：哪些逻辑不能放在 API 层？

口播版：不能把真正的业务状态变更和一致性控制放在 API 层。API 层可以做鉴权和参数转换，但订单状态怎么变、库存怎么扣、优惠券怎么锁，应该由对应 RPC 服务负责。否则多个入口调用同一业务能力时会出现规则不一致，比如普通订单 API 和 AI 下单入口如果各自实现一套订单逻辑，就很容易出现一个入口有校验、另一个入口绕过校验的情况。所以项目里 AI 高风险下单最后仍走订单内部 API 或业务 RPC 路径，可信用户身份由服务端注入，业务规则仍复用原链路。

追问 2：那为什么订单创建入口还在 API 层用了 Saga？

口播版：这是因为 Saga 本身更像跨服务业务流程编排，而不是某一个服务的内部状态更新。订单创建涉及结算状态、优惠券锁定和订单创建三个服务，放在单个 RPC 内会让这个 RPC 对其他服务耦合过重，也不利于对外入口统一控制。API 层拿到登录态用户后构造 Saga，把每个服务的正向动作和补偿动作串起来；每个服务内部仍然只处理自己的本地事务和业务状态。这样跨服务流程在入口编排，本地一致性在服务内部保障，职责边界更清楚。

#### 3. 这个项目最核心的后端链路是什么？

口播版：最核心的是从结算到下单再到支付和资源释放的链路。用户先发起结算，结算服务生成预订单、做请求指纹幂等、调用库存预扣，并保存商品快照和金额。然后创建订单时，API 层通过 DTM Saga 锁定优惠券、锁定结算状态、创建订单记录。如果支付发生，会创建支付单、生成支付链接、推进订单到支付中状态；支付成功后通过回调写支付结果，并用 outbox 投递支付成功事件，推动优惠券使用和订单成功状态。订单取消、订单超时、支付超时则通过延时扫描和 Kafka 消费释放库存、优惠券和结算资源。

追问 1：为什么要先有结算单，再创建订单？

口播版：结算单承担的是“用户确认购买前的资源预占和金额快照”。如果用户直接创建订单，系统要同时查商品、扣库存、算优惠、锁券、写订单，链路很长且失败回滚复杂。先创建结算单后，可以把商品快照、预扣库存、优惠金额这些信息固定下来，后续下单只需要基于 pre_order_id 和地址等参数创建最终订单。这样也方便处理用户确认、AI 高风险确认和超时释放，因为预订单有自己的生命周期，过期就释放预占资源，不会长期占用库存。

追问 2：链路中哪些地方最容易出事故？

口播版：我认为主要有三类：第一是重复提交，例如用户连点结算或支付，可能导致重复预扣、重复下单或重复支付单；第二是跨服务部分失败，例如订单创建成功但优惠券或库存状态没有正确推进；第三是超时资源没有释放，例如预订单、待支付订单和支付单过期后仍占库存。项目里针对这些问题分别用了请求指纹幂等、Saga 补偿、本地事务、Outbox 事件、Redis ZSET 延时扫描和状态机校验。面试里我会强调这是组合治理，不是某一个技术点单独解决所有问题。

### 主题二：交易一致性与幂等

#### 4. 创建订单为什么用了 DTM Saga？

口播版：创建订单不是单服务操作，它要先确认结算单可以进入下单状态，如果使用优惠券还要锁定用户优惠券，最后才能创建订单记录。这里涉及 checkout、coupons、order 三个服务，不能用单库事务保证一致性，所以我在订单 API 层使用 DTM Saga，把每个正向步骤和补偿步骤注册进去。比如锁券对应释放券，锁结算状态对应回滚结算状态，创建订单对应订单创建回滚。Saga 提交时设置全局超时并等待结果，失败后会根据业务错误或 gRPC 错误映射成客户端可理解的错误码。这个设计的核心是承认跨服务只能做到最终一致，并把失败恢复路径显式建模。

追问 1：Saga 和 TCC 有什么区别？为什么这里更适合 Saga？

口播版：TCC 强调 Try、Confirm、Cancel 三阶段，适合资源预留语义特别明确、强一致要求更高的场景；Saga 更像一串本地事务加补偿动作，适合业务步骤已经天然存在正向和逆向操作的流程。这个项目里结算状态锁定、优惠券锁定、订单创建都有相对明确的补偿操作，而且链路是用户下单这种业务流程，不一定需要每个资源都抽成 TCC 三阶段。库存预扣已经在结算阶段完成，创建订单阶段主要是状态推进，因此 Saga 的实现成本和业务表达更合适。当然，如果未来要求更强的资源确认语义，库存和优惠券也可以进一步演进成更完整的 TCC。

追问 2：如果 Saga 补偿也失败怎么办？

口播版：补偿失败不能靠同步请求一直卡住用户，所以需要把补偿失败变成可重试、可观测、可人工介入的问题。项目里部分后置释放是通过 outbox 和 Kafka 异步完成，dispatcher 会按重试策略投递，消费者也会通过业务状态判断是否可以重复执行。对于 Saga 本身的补偿失败，DTM 会保留事务状态并重试，服务内补偿接口必须设计成幂等，比如重复释放结算状态或优惠券时要根据当前状态判断。如果补偿最终不可恢复，就应该有日志、状态表和告警支撑人工修复，而不是让客户端重试导致更大不一致。

#### 5. 结算预订单如何保证幂等？

口播版：结算预订单的幂等基于请求指纹实现。结算服务会把用户 ID、优惠券 ID、商品 ID 和数量排序后拼成稳定字符串，再做 SHA256，形成 Redis key。用户在短时间内提交相同结算请求时，Redis Lua 会检查 key 是否存在，如果存在就直接返回已有 pre_order_id，如果不存在才写入新的 pre_order_id，并继续走库存预扣和结算记录写入。这样可以避免用户重复点击或网络重试造成多个预订单和多次库存预扣。这个 key 设置了 300 秒 TTL，是为了覆盖短期重复提交窗口，长期一致性则由预订单状态和超时释放控制。

追问 1：为什么商品要排序后再生成指纹？

口播版：因为同一组商品在请求里的顺序不应该影响业务语义。用户买 A 两件、B 一件，和请求体里先传 B 再传 A，本质上是同一个结算请求。如果不排序，两个请求会生成不同 key，幂等就失效了。项目里按 product_id 升序，如果 product_id 相同再按 quantity 升序，这样相同商品集合能得到稳定指纹。这个细节看起来小，但面试里能说明我考虑的是业务幂等，而不是简单拿原始 JSON 做 hash。

追问 2：Redis 写入成功但后续库存预扣失败怎么办？

口播版：这个场景必须清理幂等 key，否则用户再提交同样请求会拿到一个实际上没有完成的 pre_order_id。项目里在发现商品为空、库存预扣失败、结算事务写入失败等路径，会删除对应 Redis key，并在库存已经预扣但后续失败时调用 ReturnPreInventory 做同步回滚。这个处理说明幂等 key 不是简单防重复，它代表“这个请求已经进入可复用结果”。如果结果没有完整建立，就要清理 key，让用户下一次请求有机会重新执行完整流程。

#### 6. 库存预扣为什么用 Redis Lua？

口播版：库存预扣涉及多个原子步骤：检查这个预订单是否已经处理过、检查每个商品库存是否足够、批量扣减库存、设置预扣标记。如果这些步骤拆成多次 Redis 命令，在并发下会出现检查通过但扣减时库存已变化的问题，也可能重复扣同一个预订单。Lua 脚本在 Redis 内部原子执行，可以把这些动作合成一个不可打断的过程。项目里的脚本先判断锁 key 是否存在，存在说明已处理；再遍历商品库存，不足时删除锁并返回库存不足；最后批量 `DECRBY` 并设置预扣标记 TTL。这个设计主要解决并发扣减和重复执行两个问题。

追问 1：库存预扣和真实扣库存有什么区别？

口播版：预扣库存是在用户进入结算或待支付阶段时先占用库存，防止用户已经看到可购买结果但后续下单时库存被别人抢走；真实扣库存更像支付成功或订单最终确认后的库存消耗。从用户体验和交易流程看，预扣能降低下单阶段失败概率，但代价是需要处理超时释放和订单取消释放。这个项目在结算阶段预扣，在订单取消、订单超时、支付超时等事件中释放资源，支付成功后则推进订单和相关状态。也就是说预扣是生命周期管理问题，不只是扣减一个数字。

追问 2：Redis 库存和数据库库存如何一致？

口播版：这个项目当前更偏向用 Redis 承担高并发库存扣减入口，数据库模型保留库存数据。严格来说，Redis 和数据库库存的一致性需要初始化、回写、补偿校验和定期对账配合，不能只靠 Lua 保证。面试时我会诚实说明：代码里重点落在 Redis 原子预扣、释放和业务链路协同，生产级还需要补充库存流水、定时对账、异常修复任务和监控告警。这样回答比直接说“Redis 保证一致”更准确，因为 Redis 只能保证脚本内部原子性，不能自动保证跨存储一致性。

#### 7. 支付单如何处理重复创建？

口播版：支付服务创建支付单时，首先会按 order_id 查询是否已有支付单。如果已经存在，就直接返回已有支付单；如果支付单仍是未支付状态，还会重新保存支付超时任务。只有查询不到已有支付单时，才会调用订单服务获取可支付订单信息，校验支付方式，生成第三方支付链接，写入支付单，并推进订单状态到支付中。这样设计是为了应对用户重复点击支付、前端重试或网络抖动。支付单幂等的核心键是订单 ID，因为一个订单在同一支付阶段不应该生成多个有效支付单。

追问 1：为什么支付创建后还要更新订单状态？

口播版：支付单创建代表用户已经进入支付流程，订单状态应该从待支付或已创建推进到支付中，这样后续订单查询、超时处理和支付回调都能根据状态判断。否则支付单存在但订单仍停留在旧状态，会导致用户侧状态不一致，也可能让超时任务走错分支。项目里支付服务创建支付单后调用订单 RPC 更新订单支付状态，如果更新失败则返回错误。这里还有进一步优化空间，比如通过本地消息或事务编排保证支付单和订单状态推进的一致性，但当前代码已经体现了状态推进的必要性。

追问 2：支付回调为什么适合用 Outbox？

口播版：支付回调通常是第三方平台异步通知，处理时要先保证本地支付结果落库，然后再通知订单、优惠券等服务。如果直接在回调请求里同步调用所有下游，只要某个服务短暂失败，就可能导致第三方反复通知或本地状态与下游状态不一致。Outbox 的好处是把“支付成功事实”和“待发送事件”放在本地事务里一起提交，之后由后台异步投递 Kafka。这样回调可以快速确认本地事实，下游推进通过可靠消息慢慢完成，失败也有重试和状态记录。

### 主题三：AI 客服与工具调用

#### 8. AI 客服的主链路是怎样的？

口播版：用户请求先进入 `apis/ai` 的 `/douyin/ai/chat`，网关通过现有认证中间件拿到登录态用户 ID，设置 SSE 响应头，校验请求 JSON，然后调用 `services/aiagent` 的 server-streaming RPC。AI Agent 服务先通过 Conversation Manager 准备会话，保存用户消息并处理 client_message_id 幂等；然后可选执行 RAG 准备上下文，再调用 Eino Supervisor Agent。Agent 运行过程中，模型可能输出思考、子 Agent 路由、工具调用、工具结果、确认请求或最终回答，服务把这些转成统一 AgentEvent 并流式返回。网关再把事件写成 SSE 格式，最后发送 `event: done`。

追问 1：为什么用 POST + SSE，而不是 WebSocket？

口播版：这个项目的交互是典型的一问一答流式响应，客户端发一个 JSON 请求，服务端持续返回事件，POST + SSE 能很好覆盖这个场景。相比 WebSocket，SSE 在服务端实现、HTTP 鉴权、网关代理、调试和压测上更简单，JMeter 也可以通过 JSR223 自定义采样读取事件流。当然，如果未来需要客户端和服务端长连接双向频繁交互，比如多个任务同时取消、编辑、订阅，WebSocket 会更合适。当前选择 SSE 是为了让协议复杂度匹配业务需求。

追问 2：client_message_id 的作用是什么？

口播版：client_message_id 是用户消息级别的幂等键。AI 请求可能因为网络、前端重试或压测工具重复发送，如果每次都触发模型和工具调用，可能造成重复写操作，尤其是 AI 下单或取消订单这类高风险动作。项目里 Conversation Manager 会保存用户消息，并用 user_id 和 client_message_id 做重复检测；如果发现重复请求，就不再执行模型和工具，而是重放已经保存的 assistant 消息。这个设计把 AI 对话也当成业务请求处理，而不是普通聊天文本。

#### 9. 为什么要设计 Tool Registry？

口播版：Tool Registry 是 AI 可以调用哪些业务能力的单一事实来源。它不只是列工具名，还记录工具描述、参数 schema、风险等级、是否写操作、是否需要确认、超时时间、对应 RPC 服务和方法。这样做的原因是模型输出不可信，不能让它随便指定一个函数名或参数去执行。Registry 可以给不同子 Agent 暴露不同工具，也可以让执行器在运行时拿到 metadata 做超时、重试、确认和审计。我的理解是，AI 工具调用的难点不是把函数暴露给模型，而是把可调用能力变成可治理、可审计、可扩展的业务接口。

追问 1：工具 schema 为什么不能包含 user_id？

口播版：因为 user_id 是权限边界，必须来自登录态或服务端认证上下文，不能来自模型，也不能来自客户端请求体。模型如果可以传 user_id，就可能在幻觉或提示注入影响下访问别人的订单、优惠券或地址。项目里工具执行上下文会注入可信 user_id，handler 调业务 RPC 前使用这个 user_id 构造请求；如果客户端在 AI 请求里提交 user_id，网关也会拒绝。这个规则贯穿了 API、Agent、工具和数据查询层，是 AI 接入业务系统时最重要的安全底线。

追问 2：工具目录如何支持分域 Agent？

口播版：工具定义里有 kind 和 visibility，Registry 可以导出 root agent、all agents 和 sub agents 可见的工具。Supervisor 本身主要负责意图识别和路由，商品 Agent 只拿商品搜索、详情、推荐和库存查询，订单 Agent 拿订单查询和取消，购物车结算 Agent 拿购物车、结算和创建订单相关工具。这样模型虽然强，但每个子 Agent 的能力边界更窄，减少误调用概率，也让 prompt 更聚焦。面试时我会强调这不是简单拆 prompt，而是工具可见性和职责边界一起拆。

#### 10. Execution Guard 解决了哪些问题？

口播版：Execution Guard 解决的是“模型输出到真实业务执行”之间的安全与可靠性问题。工具调用进入执行器后，会先从上下文取可信用户身份、会话 ID、消息 ID、token 等信息，再解析参数、清理敏感字段，按工具 metadata 设置超时，调用真实业务 handler。错误会被分成临时错误和永久错误：查询工具遇到超时、网络抖动等临时错误可以有限重试，写操作默认不自动重试，避免重复写入。无论成功失败，结果都被封装成 envelope，并记录工具调用和审计。这样模型看到的是结构化结果，不会把底层错误直接暴露给用户，也不会把失败误认为成功。

追问 1：为什么查询工具可以重试，写工具不自动重试？

口播版：查询通常是幂等的，短暂网络抖动或下游不可用时，有限重试能提高成功概率，而且不会改变业务状态。写操作则不同，例如加入购物车、领取优惠券、创建订单、取消订单，重复执行可能产生副作用。即使有些写操作业务上做了幂等，也不能默认所有写工具都安全重试，所以项目里写工具默认不自动重试，高风险写操作还必须经过确认。这个设计体现的是保守原则：宁可让用户重试或进入明确失败，也不能悄悄放大副作用。

追问 2：工具调用失败后为什么不能抛普通 error 给模型？

口播版：如果直接抛普通 error，Agent 框架可能把它当成运行异常，导致整个对话中断，或者模型拿到底层错误后生成不稳定总结。项目里执行器会把可预期工具失败转换成结构化 `tool_result`，里面有 status、tool_name、attempt_count、retry_count、business_outcome、error 和 attempt_trail。这样模型可以基于明确失败给用户解释，系统也能记录失败原因和耗时。真正需要中断的，是模型不可用或框架级异常；业务工具失败应该变成可观测、可表达的业务结果。

#### 11. 高风险操作确认是怎么做的？

口播版：高风险操作包括创建订单、取消订单、删除购物车等，模型不能直接执行。项目里通过工具 metadata 标记高风险且需要确认的写操作，Eino middleware 在工具真正执行前创建确认请求，保存 tool_name、脱敏参数、summary、user_id、conversation_id、run_id 和 checkpoint_id，然后通过 interrupt 返回 `confirmation_required` 事件。前端展示确认卡片，用户批准后调用 `confirm_action`，服务端用 confirmation_id 重新校验用户、会话、状态和过期时间，再通过 checkpoint 和 interrupt_id 恢复原工具调用。执行完成后确认记录从 approved 变成 executed 或 failed。

追问 1：用户重复点击确认会不会重复下单？

口播版：不会按设计重复执行。确认处理先用 Redis 短锁合并同一个 confirmation_id 的并发请求，拿不到锁会返回 busy；即使 Redis 不可用，也会降级到 MySQL 条件更新。数据库更新要求当前状态必须是 pending 才能变 approved，执行完成后必须是 approved 才能变 executed 或 failed。也就是说只有一个请求能成功领取执行权，其余重复确认会因为状态不满足被拒绝。这里 Redis 是优化并发冲突，MySQL CAS 才是最终事实来源。

追问 2：如果用户拒绝确认，为什么不恢复 checkpoint？

口播版：拒绝确认表示用户明确不执行这个高风险动作，后端应该直接收口，而不是恢复 Agent 让模型继续围绕旧确认请求生成内容。项目里 rejected 是终态，服务端会直接持久化取消结果和最终 assistant 消息，不调用业务 RPC，也不恢复 checkpoint。这样可以避免模型继续复述或再次尝试执行同一个高风险工具。只有 approved 才需要用 checkpoint 恢复原工具调用，因为那代表用户授权执行原来被中断的动作。

### 主题四：流式响应、上下文与 RAG

#### 12. SSE 事件怎么从 Agent 传到前端？

口播版：内部是两段流式桥接。第一段在 `services/aiagent`，Eino ADK Runner 产生 iterator 事件，代码消费这些事件并转成领域层 AgentEvent，比如思考增量、工具开始、工具结果、确认请求、最终助手消息和错误。第二段在 `apis/ai`，网关调用 aiagent 的 server-streaming RPC，循环 Recv 事件并映射成前端 ServerEvent，按 SSE 格式写出 `event:`、可选 `id:`、`data:`，每次写完立即 flush。网关还有 10 秒心跳和 5 分钟请求超时。这样前端可以实时看到工具执行过程，而不是等整个 Agent 完成后一次性返回。

追问 1：为什么要区分 `tool_progress` 和 `tool_result`？

口播版：工具调用通常比普通文本生成慢，尤其是订单、库存、优惠券这种 RPC。如果只有最终结果，用户会觉得 AI 卡住了，也不利于压测时判断模型首 token 快还是工具慢。`tool_progress` 表示模型已经决定调用某个工具并开始执行，`tool_result` 表示工具返回了成功或失败。这个区分让前端可以展示运行态，也让 JMeter 或日志能统计首个工具事件耗时和工具执行耗时。它本质上是把黑盒 Agent 拆成可观察的生命周期事件。

追问 2：为什么最终回答只认 supervisor 的 final assistant message？

口播版：因为子 Agent 的输出更多是中间推理或工具选择过程，不一定适合作为用户最终答案。如果把每个 Agent 的 streaming content 都直接拼给用户，可能会出现多段重复、半成品或内部路由信息暴露。项目里把 Supervisor 作为最终对用户负责的聚合者，子 Agent 负责局部工具选择和结果整理，最终由 Supervisor 汇总成中文回答。这样职责更清晰，用户可见输出也更稳定。callback 只适合做日志、trace 和 metrics，不再承担用户可见输出。

#### 13. 多轮上下文如何控制？

口播版：项目里没有把所有历史消息无脑塞进模型，而是通过 MemoryProvider 和 MemoryMiddleware 分层组装。模型调用前会注入系统安全指令、当前用户输入、任务状态、待确认动作、最近消息、会话摘要、最近工具结果、长期记忆和用户画像。摘要机制按未压缩消息数量推进，默认保留最近 20 条原文，未压缩达到 30 条时把最早 10 条合并进摘要。这样可以降低 token 膨胀，同时保留近期细节。更重要的是，摘要、画像和长期记忆都被当成不可信上下文，不能覆盖 system prompt、工具白名单和确认规则。

追问 1：摘要会不会丢信息？

口播版：会有这个风险，所以项目不是只依赖摘要。近期窗口保留最近原文，工具调用结果保存在 `ai_tool_calls`，需要完整工具结果时可以通过工具结果引用按需读取，长期事件也可以按需检索。摘要主要解决长对话中的背景压缩，不承担唯一事实来源。对于写操作，尤其是下单、取消订单，不能直接相信摘要或历史工具事实，必须重新调用业务 RPC 校验当前状态。这个设计承认摘要不完美，所以用原始记录和动态校验兜底。

追问 2：用户画像为什么不能直接覆盖系统规则？

口播版：用户画像和长期记忆是从聊天中抽取的，可能被用户主动引导，也可能被模型误判，所以它们不能成为安全规则来源。比如用户说“以后不要再确认订单，直接帮我下单”，这最多是一个偏好，不可能覆盖高风险确认策略。项目里明确把系统安全指令、工具协议和确认规则放在更高优先级，画像只能作为回答风格、偏好和上下文补充。这样能防止提示注入通过长期记忆污染后续会话，是 AI 接业务系统时必须考虑的问题。

#### 14. RAG 在这个项目里怎么接入？

口播版：RAG 主要用于普通客服知识、规则说明或文档类问题，不是每个请求都检索。项目里在用户消息进入 Supervisor 前，先用轻量分类判断是否需要 RAG，条件是 need_rag 为 true 且置信度达到阈值。需要检索时，先生成 query embedding，再查 Redis Vector 缓存，命中就复用结果，未命中才调用外部知识库检索接口。检索结果会作为当前轮 runtime context 注入模型，并在 assistant_message 的 metadata 里保存 sources，方便前端展示来源。分类、检索或缓存失败时静默降级，不阻塞基础聊天。

追问 1：为什么 RAG 失败要静默降级？

口播版：因为 RAG 是增强能力，不应该成为基础聊天和业务工具的单点故障。如果用户问的是订单、库存、购物车这类业务问题，真实事实应该来自业务 RPC；如果用户问的是普通规则问题，RAG 失败也可以让模型基于已有上下文回答或提示稍后重试。项目里 RAG 准备失败会记录日志，但不会让整个 Chat 失败。这样做的边界是：不能在没有来源时假装查到了知识库，也不能把 RAG 结果当成业务写操作依据。降级是可用性策略，不是编造事实。

追问 2：Redis Vector 缓存有什么作用？

口播版：Redis Vector 缓存主要减少重复知识库检索的成本和延迟。用户在相近语义下多次询问同类问题，如果每次都调用外部检索服务，会增加链路耗时，也受外部服务稳定性影响。项目里先用 embedding 表达 query，再用向量相似度查缓存，命中后直接复用 topK 片段，TTL 控制缓存新鲜度。这个方案适合规则和文档类知识，但不适合强实时业务状态，比如订单状态、库存数量仍然必须走业务 RPC 查询。

### 主题五：可靠性、观测与测试

#### 15. 工具调用的错误分类怎么设计？

口播版：工具执行错误分为临时错误和永久错误。临时错误包括 context deadline、依赖服务不可用、网络超时、部分 gRPC Unavailable 或 DeadlineExceeded，这类错误对查询工具可以有限重试。永久错误包括参数错误、权限错误、业务拒绝、资源不存在、未实现工具等，这类重试没有意义，应该直接返回明确失败。写操作遇到超时时，业务结果可能是 unknown，因此更要谨慎，不能自动重复执行。项目里错误会被转换成安全错误码和用户可理解的提示，并记录 attempt trail，方便事后知道每次尝试是否真的发起了 RPC、耗时多少、失败类型是什么。

追问 1：为什么要隐藏底层错误？

口播版：底层错误可能包含连接串、数据库信息、token、内部服务名或其他敏感信息，直接暴露给模型或用户都不安全。更重要的是，模型拿到底层错误后可能生成不稳定解释，甚至误导用户。项目里对外只暴露稳定错误码和安全提示，比如依赖服务暂时不可用、参数不正确、无权执行工具等；原始错误进入结构化日志和服务端记录。这样既保护内部信息，又保留排障证据。安全提示不是吞错，而是把错误分成“用户该知道的”和“工程排障该看的”。

追问 2：如果业务已经执行但审计失败怎么办？

口播版：这个情况不能简单返回成功，也不能让用户重试，因为重试可能造成重复写入。项目里写操作成功后会记录工具调用和审计，如果审计记录失败，会返回失败事件，但标记 business_executed 为 true，并提示业务结果已经产生但审计失败，需要联系支持或避免重复操作。确认状态也会按已经执行的事实推进，避免同一个确认再次执行。这个细节体现了对“未知状态”和“已执行但后处理失败”的区分，是写操作可靠性里很重要的边界。

#### 16. 你怎么做测试和验证？

口播版：这个项目的测试分层比较明显。业务服务层有用户、商品、库存、订单、优惠券、支付等 RPC 测试；AI 侧有模型工厂、消息转换、工具注册、执行器重试、确认状态机、上下文、记忆、RAG client、SSE 网关逻辑等测试。对于 AI 客服，重点不是只测模型能不能回复，而是测安全边界，比如模型传 user_id 会不会被覆盖，跨用户会话和确认能不能拒绝，过期或重复确认会不会执行，工具失败会不会被总结成成功。压测方面，我用 JMeter 对 SSE 接口统计完整连接耗时、首个 SSE 事件、首个 assistant delta、首个工具事件和工具执行平均耗时。

追问 1：为什么 AI 接口压测不能只看 JMeter 聚合报告的平均响应时间？

口播版：SSE 是长连接，聚合报告的 Load Time 往往代表整个流式请求持续时间，不等于用户感知的首响。用户实际更关心首个业务事件多久出现、模型什么时候开始输出、工具什么时候开始和结束。尤其是 AI 客服里，一个请求可能包含模型推理、工具调用、确认、最终总结，如果只看总耗时，很难判断瓶颈在模型 provider、业务 RPC 还是 SSE 网关。所以我用 JSR223 精确采样器解析 SSE 行，统计 first_sse_event_ms、first_assistant_delta_ms、first_tool_event_ms 和 tool execution duration，再结合服务端日志定位。

追问 2：如果压测 100 并发遇到模型 provider 429，你怎么解释？

口播版：这说明压测碰到的不一定是我后端服务瓶颈，而是上游模型 provider 的并发限制。比如 provider 限制是 35，那么 100 个并发同时触发模型调用会得到 429。这个结果可以说明“端到端用户体验在外部模型限制下不可用”，但不能直接说明后端只能扛 35 并发。如果要测后端容量，需要加本地并发限流或队列，把 provider 并发控制在 35，观察排队时延；或者使用 mock model 隔离外部限制。面试时我会把“后端容量”和“依赖模型限额”分开解释。

#### 17. 可观测性怎么做？

口播版：项目里可观测性包括三层。第一是结构化日志，AI 网关、Agent、工具执行、确认、RAG、上下文都会带 component、stage、conversation_id、user_id、tool_call_id、run_id 等字段，便于链路定位。第二是 Prometheus 和 Grafana，通过 go-zero 的 metrics 暴露 runtime、process 和服务指标，Grafana dashboard 查询 Prometheus 数据展示服务在线状态、CPU、内存和 goroutine。第三是 Jaeger 链路追踪，各服务配置 Telemetry 后可以看到跨 API/RPC 调用路径。对 AI 系统而言，日志尤其重要，因为模型输出和工具执行是动态链路，需要把事件和上下文 ID 记录清楚。

追问 1：Grafana 连 Prometheus 时为什么不能用 localhost？

口播版：如果 Grafana 跑在 Docker 容器里，Grafana UI 里配置的数据源 URL 是 Grafana 后端容器去访问，不是浏览器访问。`localhost` 在容器里指 Grafana 自己，所以访问 `localhost:9091` 会连接失败。Prometheus 和 Grafana 在同一个 Docker network 时，应该用服务名和容器内部端口，比如 `http://prometheus:9090`。宿主机浏览器访问 Prometheus 才用端口映射，比如 `http://localhost:9091`，这里要区分宿主机端口和容器内部端口。

追问 2：targets 是 UP 但 dashboard 没数据怎么排查？

口播版：targets UP 只能证明 Prometheus 能抓取目标，不代表 dashboard 查询的指标一定存在。排查时我会先在 Grafana Explore 里查 `up`，确认数据源工作；再查 dashboard 用到的指标，比如 `process_cpu_seconds_total`、`go_goroutines`、业务指标等；然后检查 dashboard 的 Job 变量是否选择 All，以及时间范围是否覆盖数据。像 `rate(...[5m])` 这类查询还需要至少两个采样点，服务刚启动可能短暂为空。这个问题本质是数据源、指标名、label 和时间窗口四个层面的匹配。

#### 18. 这个项目你觉得最大的难点是什么？

口播版：最大的难点不是单个技术点，而是把 AI 的不确定性接入真实电商写操作时，如何保持后端系统的安全边界。传统电商接口只要客户端传参、服务端校验、写数据库；AI 客服多了一层模型，它会生成工具名和参数，还可能受提示注入影响。因此我重点做了工具白名单、可信用户身份注入、高风险确认、工具失败结构化返回、审计和上下文优先级控制。另一方面，电商本身已有下单、库存、优惠券、支付这些一致性问题，所以 AI 不能绕过原业务链路。最终设计是让 AI 只做编排入口，业务事实仍来自原 RPC。

追问 1：如果重新做一版，你会优化什么？

口播版：我会优先补三类能力。第一是观测指标，把目前比较多的结构化日志沉淀成 Prometheus 指标，例如工具成功率、确认转化率、模型首 token、工具 P95、RAG 命中率。第二是后端压测隔离，把真实模型、mock model 和限流队列三种压测模式分开，避免 provider 限额干扰后端容量判断。第三是交易链路的对账和修复，把库存、优惠券、订单、支付之间的最终一致性补偿做成更系统的后台任务。这样项目从“功能闭环”会更接近“生产治理闭环”。

追问 2：你如何向面试官证明这些不是包装？

口播版：我会从源码证据讲，而不是只讲概念。比如微服务交易一致性可以直接看订单 API 的 Saga 编排和各服务补偿接口；库存可靠性可以看 Redis Lua 脚本和结算请求指纹；可靠事件可以看 outbox dispatcher、订单取消 outbox 和支付回调保存事件；AI 工具安全可以看 Tool Registry、Executor、retry 分类和审计 recorder；确认幂等可以看 ConfirmationManager、Redis lock 和 MySQL 条件更新；SSE 可以看网关如何写 `event:` 和 `data:`。每个简历 bullet 都能落到具体文件和测试，这样就不是空泛包装。
