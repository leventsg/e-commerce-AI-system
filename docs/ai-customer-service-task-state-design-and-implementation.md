# AI 智能客服 TaskState：长期事件设计与实施方案

> 本文重新定义本项目中的 TaskState。它不再表示长任务的步骤、暂停点或恢复状态，而表示从用户长期重要事件中生成的“客户连续性状态”。本文侧重设计思想、业务流程和组件职责，不展开数据库建表、并发控制和具体代码实现。

## 1. 结论先行

AI 智能客服中的大多数任务都很短：查询订单、推荐商品、领取优惠券、修改购物车、取消订单，通常在一次或几次对话内完成。为这些任务建设一套独立的长任务状态机、执行租约和崩溃恢复机制，成本大于收益。

但是，客服对话虽然短，用户关系却是长期的。用户可能隔几天、几周甚至几个月再次进入新的会话。如果系统完全忘记过去发生过的重要事情，客服就会表现得像第一次见到用户：重复询问、忽略历史投诉、给出与既往经历冲突的建议。

因此，本项目保留 `TaskState` 这个名字，但赋予它新的项目内含义：

> **TaskState 是系统根据用户长期重要事件，围绕当前客服任务生成的一份有边界、可追溯、因 Agent 而异的客户连续性状态。**

它由两层组成：

1. **长期事件事实层**：保存过去真正发生过、未来仍可能有服务价值的重要事件。
2. **TaskState 投影层**：面对当前问题时，从长期事件中选出少量相关内容，形成一次性的上下文视图。

长期事件会持久保存；TaskState 投影按请求动态生成，通常不需要单独持久化。

## 2. 为什么智能客服需要长期事件

### 2.1 短任务不等于没有长期上下文

单次客服任务可能只持续几十秒，但服务质量往往依赖更长时间尺度的信息。例如：

- 用户上次购买同类商品后发生过严重质量问题，本次推荐时应避免重复踩坑。
- 用户曾因配送延迟正式投诉，本次再次询问物流时应更谨慎地解释和处理。
- 用户明确表示某类商品不适合自己，后续推荐不应反复出现。
- 用户曾完成一次重要售后，新的客服应知道事件背景，而不是要求用户从头复述。
- 用户明确纠正过某项长期偏好，旧偏好不应继续影响回答。

这些信息不是当前短任务的执行进度，却决定了客服是否具有连续性和同理心。

### 2.2 长期事件解决的核心问题

长期事件主要带来四种价值：

- **减少重复沟通**：用户不必在每个新会话中重新描述重要背景。
- **保持服务连续性**：不同时间、不同 Agent 对同一用户形成一致认知。
- **改善决策质量**：推荐、售后解释和风险提醒能够参考真实历史经历。
- **提供可解释性**：模型使用的长期信息可以追溯到具体消息、工具结果或业务事件。

### 2.3 它不负责什么

TaskState 不是万能记忆，也不是业务数据库的副本。它不负责：

- 保存当前订单、库存、价格、优惠券是否可用等实时状态；这些必须重新查询业务 RPC。
- 保存每句聊天、每次点击和每个工具调用；普通流水没有长期记忆价值。
- 保存访问令牌、支付凭证、完整地址、身份证号等敏感信息。
- 代替会话消息和会话摘要；摘要服务当前会话，长期事件服务跨会话连续性。
- 控制工具执行、人工确认和写操作权限；这些仍由 Execution Guard、Confirmation Manager 和业务服务负责。

## 3. TaskState、长期事件和其他上下文的边界

| 对象 | 回答的问题 | 生命周期 | 事实来源 |
| --- | --- | --- | --- |
| 最近消息 | 刚才具体说了什么 | 当前会话 | `ai_messages` |
| 会话摘要 | 当前会话讨论过什么 | 当前会话及后续压缩 | 消息摘要 |
| 用户画像 | 用户现在相对稳定的偏好是什么 | 长期、可更新 | 多次明确表达和验证结果 |
| 长期事件 | 过去发生过什么重要事情 | 跨会话、可过期或撤回 | 用户消息、成功工具结果、业务事件 |
| TaskState | 哪些历史事件与当前客服任务有关 | 单次请求或单次 Agent 调用 | 长期事件的动态投影 |
| 业务实时状态 | 订单、库存等现在是什么状态 | 实时 | 业务 RPC |

一个简单判断方法是：

- “用户通常偏爱黑色”属于用户画像。
- “用户上个月明确把颜色偏好从白色改成黑色”属于长期事件。
- “当前正在问黑色耳机，过去有两次相关购买和一次质量投诉”属于本次 TaskState。
- “某个耳机现在是否有库存”必须调用库存服务。

## 4. 什么内容值得成为长期事件

### 4.1 事件准入原则

一条信息只有同时满足以下条件，才应进入长期事件：

1. **已经发生或被用户明确表达**，而不是模型推测。
2. **未来仍可能影响客服服务**，不是只对当前一句话有用。
3. **具有一定重要性**，遗忘它可能造成重复询问、冒犯、错误推荐或低质量服务。
4. **有可追溯证据**，能够关联到消息、工具调用或可信业务事件。
5. **符合隐私和最小化原则**，不保存无关敏感内容。

可以用一句业务问题检验：

> 如果用户一个月后再次来咨询，客服知道这件事是否仍然有帮助？

如果答案是否定的，就不应该长期保存。

### 4.2 建议保存的事件类型

| 类型 | 含义 | 示例 |
| --- | --- | --- |
| 重要消费里程碑 | 对后续服务有明显价值的购买经历 | 首次购买某类耐用品、完成重要换新 |
| 重大服务事件 | 投诉、纠纷、严重配送或质量问题 | 曾因破损商品投诉并完成补偿 |
| 售后结果 | 值得跨会话保留的退换、退款结果 | 某类商品连续两次因尺寸问题退货 |
| 明确偏好变化 | 用户主动表达且预计持续的变化 | 明确表示以后不再推荐某品牌 |
| 服务约定 | 客服与用户形成、仍可能影响后续服务的约定 | 已承诺后续咨询优先核对某项问题 |
| 用户纠正 | 用户对历史记忆作出的明确更正 | 用户说明此前记录的偏好已经失效 |

事件类型应采用白名单。新增类型时必须说明它对未来客服决策有什么价值，不能仅因为“可能有用”就无限扩张。

### 4.3 不应保存的内容

- 普通问候、闲聊和一次性问题。
- 每次商品浏览、搜索词和购物车小改动。
- 短时间内会变化的订单状态、库存数量和商品价格。
- 模型推断出的收入、健康、家庭关系、性格或消费能力。
- 没有明确证据的“用户喜欢”“用户讨厌”。
- 完整工具入参、完整工具返回、原始长对话。
- 密码、令牌、验证码、银行卡、完整地址等敏感字段。

## 5. 长期事件保存哪些字段

长期事件保存的是“紧凑事实及其依据”，而不是原始材料的复制品。

| 字段 | 作用 | 设计要求 |
| --- | --- | --- |
| `event_id` | 事件唯一标识 | 便于引用、纠错和删除 |
| `user_id` | 事件所属用户 | 只能来自认证上下文，模型和客户端不得提供或覆盖 |
| `event_type` | 事件类别 | 必须来自白名单 |
| `summary` | 简洁描述发生了什么 | 只保存客服真正需要的事实，不保存长篇对话 |
| `occurred_at` | 事件实际发生时间 | 与数据库写入时间区分 |
| `keywords` | 检索标签 | 商品类别、服务主题、问题类型等非敏感词 |
| `related_entities` | 相关业务对象引用 | 可保存订单、商品等最小必要标识，不复制完整业务对象 |
| `importance` | 长期服务价值 | 用于在多个相关事件中确定优先级 |
| `confidence` | 事实可信度 | 确定性工具结果高于语言推断；低于阈值不入库 |
| `source_type` | 事件来源 | 用户消息、成功工具结果或可信业务事件 |
| `source_refs` | 证据引用 | 消息 ID、工具调用 ID、业务事件 ID；用于追溯，不把原文塞进事件 |
| `status` | 当前有效状态 | `active`、`superseded`、`deleted`、`expired` |
| `supersedes_event_id` | 被本事件纠正或替代的旧事件 | 防止新旧说法同时影响模型 |
| `expires_at` | 事件失效时间 | 对有时效性的服务约定设置；永久事件可以为空 |
| `created_at` / `updated_at` | 系统维护时间 | 支持治理和审计 |

当前项目已有 `ai_user_memory_events`。它应继续作为长期事件的事实存储，不需要另外创建一套 `ai_task_states` 来重复保存相同内容。后续可以按需要补充证据、重要性、可信度、替代关系和过期时间等字段。

## 6. 谁负责产生和更新长期事件

### 6.1 总体职责

```text
用户对话 / 成功工具结果 / 可信业务事件
                    ↓
            长期事件候选生成器
                    ↓
        规则校验与事件准入判断
                    ↓
          ai_user_memory_events
                    ↓
      TaskState Selector / Builder
                    ↓
             ContextBuilder
                    ↓
          Supervisor / Domain Agent
```

各组件的责任如下：

| 组件 | 责任 |
| --- | --- |
| 事件候选生成器 | 从对话、工具结果或业务事件中发现“可能值得长期保存”的内容 |
| 事件准入判断器 | 校验证据、重要性、隐私、用户归属、事件类型和重复情况 |
| 长期事件存储 | 保存通过校验的事实，支持查询、纠错、失效和删除 |
| TaskState Selector | 根据当前问题、Agent、业务对象和时间范围选择相关事件 |
| TaskState Builder | 把选中的事件组织成本次调用所需的最小状态视图 |
| ContextBuilder | 将 TaskState 放入模型上下文，并执行长度和格式控制 |
| Agent | 使用事件辅助回答；无权直接篡改长期事件，也不能把事件当作实时业务真相 |

### 6.2 谁能决定写入

模型只负责发现和结构化“候选事件”，不能直接决定落库。最终写入由服务端规则控制：

- 用户归属必须来自认证上下文。
- 对话事件必须能追溯到当前用户的消息。
- 工具事件必须来自真实成功结果；失败或结果未知不能记录为成功事件。
- 事件类型必须在白名单中。
- 含敏感信息、价值过低、证据不足或与现有事件重复的候选应被拒绝。
- 与旧事件冲突时不能静默覆盖，要建立替代关系或等待进一步确认。

这种设计把模型放在“理解语言”的位置，把服务端放在“决定能否成为系统事实”的位置。

## 7. 长期事件在什么时候更新

长期事件不应在每轮对话后无条件写入，而应由明确触发点驱动。

### 7.1 成功业务操作后：即时更新

当工具或业务服务返回确定成功，并且结果符合重要事件标准时，可以立即生成事件。例如重大售后完成、重要投诉处理完成。

这类事件的事实来源最可靠，不需要模型猜测业务结果。工具失败、超时或执行结果未知时不得写成成功事件。

### 7.2 对话形成稳定事实后：异步更新

用户在对话中明确表达偏好变化、重要经历或历史问题时，由长期事件提取器生成候选。为避免增加客服回复延迟，这一步通常在回复完成后异步进行。

当前项目已经在会话摘要刷新后触发长期记忆提取。这条链路可以继续作为低频批处理入口；如果未来希望更及时，可在检测到“明确纠正、重大投诉、明确长期偏好”等强信号时提前触发，但不需要每轮都调用模型提取。

### 7.3 用户纠正或要求遗忘时：立即更新

当用户明确表示“这条信息不对”“以后不要再记这个”时，应立即执行纠错或删除：

- 新事实替代旧事实：新事件记为 `active`，旧事件记为 `superseded`。
- 用户要求遗忘：相关事件记为 `deleted`，并从后续检索中排除。
- 事件自然失效：达到有效期后记为 `expired`。

删除、过期和被替代的事件都不能继续注入模型上下文。

### 7.4 定期治理：合并、去重和过期

后台维护任务可以低频执行以下工作：

- 合并语义相同、来源不同的重复事件。
- 清理长期没有价值且已经过期的事件。
- 检查互相冲突的有效事件。
- 根据新的明确证据更新可信度或替代关系。

后台治理只整理事实，不能凭空创造用户事件。

## 8. TaskState 如何注入上下文

### 8.1 注入时机

TaskState 应在“已经拿到当前用户消息和目标 Agent，但模型尚未开始本次推理”时生成并注入。

推荐流程是：

1. 网关完成鉴权，获得可信 `user_id`。
2. 系统读取当前消息、最近消息和会话摘要。
3. Supervisor 首次判断问题所属领域；此时只使用极少量通用事件，或者不注入长期事件。
4. 路由到具体 Domain Agent 后，以 `user_id + 当前问题 + AgentName + 已识别业务对象` 发起事件检索。
5. TaskState Selector 执行硬过滤和相关性选择。
6. TaskState Builder 生成紧凑视图。
7. ContextBuilder 将该视图作为 `<task_state>` 注入 Domain Agent 的动态上下文。
8. Agent 回答或调用工具；需要实时状态时仍然查询业务 RPC。

这样既避免在路由前加载大量无关记忆，也能让订单、商品、优惠券等 Agent 看到各自真正需要的历史事件。

### 8.2 谁判断哪些事件适合注入

最终选择权属于服务端的 `TaskState Selector`，而不是大模型自由决定。它使用当前请求形成检索条件，并按以下顺序处理：

1. **安全过滤**：只允许当前认证用户、`active` 状态、未过期且该 Agent 有权查看的事件。
2. **任务相关性**：优先匹配当前意图、领域、商品类别、订单或其他业务对象。
3. **服务价值**：在相关事件中优先选择重要、可信、尚未解决或可能影响当前决策的内容。
4. **时间合理性**：在价值相近时优先较新的事件，但不能简单用“最新”替代“最相关”。
5. **去重与多样性**：相同事实只保留一条，避免多条类似事件挤占上下文。
6. **数量和长度限制**：通常只注入最相关的 3～5 条，并受独立 token 预算约束。

语义模型或向量检索可以帮助计算相关性，但只能产生候选排序；用户隔离、状态过滤、Agent 可见范围和数量上限必须由确定性规则兜底。

### 8.3 为什么不能注入全部事件

全量注入会产生四个直接问题：

- 无关历史干扰当前判断，增加模型误关联。
- 上下文快速膨胀，成本和延迟持续增长。
- 敏感或不必要的信息暴露给不相关 Agent。
- 旧事件可能压过当前消息和实时业务结果。

因此，“存得完整”和“给模型看得少”并不矛盾。长期事件库用于保存可治理的事实，TaskState 用于最小化披露。

### 8.4 注入内容的建议格式

TaskState 只展示模型完成当前任务所需的字段，不暴露内部评分、原始证据和用户身份字段。例如：

```text
<task_state>
与当前“耳机售后咨询”相关的长期事件：
- 2026-06：用户购买同系列耳机后曾出现左耳无声，已完成换货。
- 2026-08：用户明确表示后续更重视耐用性，不希望只按价格推荐。
使用约束：以上是历史服务背景，不代表当前订单或库存状态；实时信息必须调用业务工具确认。
</task_state>
```

如果没有足够相关的事件，就不注入 `<task_state>`。空记忆不需要用占位文本干扰模型。

## 9. 不同 Agent 如何看到不同 TaskState

长期事件属于用户，但不代表每个 Agent 都应看到全部内容。TaskState 应按 Agent 能力边界生成不同投影。

| Agent | 优先注入的事件 | 通常不需要的事件 |
| --- | --- | --- |
| Product Agent | 类目偏好变化、重大商品使用经历、相关质量问题 | 无关订单物流细节 |
| Order Agent | 相关订单经历、履约投诉、取消或售后历史 | 无关品类浏览记录 |
| Coupon Agent | 明确促销偏好、优惠使用中的重大问题 | 商品质量和物流细节 |
| Cart / Checkout Agent | 与当前商品、结算方式相关的明确历史问题 | 其他领域投诉 |
| Supervisor | 足以帮助路由的少量高层事件 | 详细证据和完整历史 |

Agent 差异由服务端配置维护，例如允许的事件类型、业务领域和最大条数。`AgentName` 只是选择策略的输入，不能用来绕过用户隔离和隐私限制。

同一事件可能对多个 Agent 有价值，但呈现粒度可以不同：Supervisor 看到一句概括，Domain Agent 在确有需要时看到更具体的事实摘要。

## 10. 检索与选择的核心流程

假设用户问：“上次那个容易坏的耳机还有类似替代品吗？”

TaskState 的生成过程如下：

1. 从当前消息识别出任务属于商品推荐，主题是耳机，线索是“上次”“容易坏”。
2. 只查询当前用户仍然有效的耳机、质量问题和偏好变化事件。
3. 排除无关的优惠券、其他品类和已经被纠正的事件。
4. 优先选中“同系列耳机故障并换货”和“用户重视耐用性”两条事件。
5. 将两条紧凑事实注入 Product Agent。
6. Product Agent 根据历史背景理解“类似替代品”的含义，但仍调用商品服务查询当前可售商品。

这个过程体现了 TaskState 的本质：它不是把历史交给模型自己翻，而是服务端先围绕当前任务做好筛选。

## 11. 更新冲突、重复和错误记忆

### 11.1 重复事件

同一事实可能同时出现在用户对话、工具结果和后续摘要中。系统应根据用户、事件类型、相关业务对象、发生时间和事实摘要识别重复，只保留一个有效事件，其他来源作为补充证据，而不是生成多条几乎相同的记忆。

### 11.2 新旧事实冲突

长期记忆不能简单“最后写入覆盖一切”。处理原则是：

- 用户明确纠正自己的偏好时，新事件替代旧事件。
- 业务结果与对话描述冲突时，可信业务结果用于事实判断，但不抹去“用户曾提出该问题”这一服务事件。
- 无法判断哪个事实正确时，两条都不应直接作为确定事实注入，应等待确认或降低可信度。

### 11.3 模型提取错误

由于长期事件可能影响未来多次服务，错误记忆比单次错误回答影响更大。因此必须允许：

- 用户查看或纠正与自己有关的记忆。
- 通过证据引用追查事件来源。
- 将错误事件删除或标记为被替代。
- 确保非 `active` 事件不会被近期事件查询遗漏过滤。

## 12. 安全与隐私边界

长期事件设计必须遵守以下不可妥协的规则：

- `user_id` 只来自登录认证上下文。
- 事件候选中的用户身份字段一律忽略或覆盖。
- 所有检索首先执行用户隔离，再计算相关性。
- 不因“个性化”而保存敏感推断。
- 注入遵循最小必要原则，不相关 Agent 不可见。
- 用户删除、过期和被替代的事件不得参与检索。
- 长期事件只影响表达、推荐和服务连续性，不能绕过工具权限、人工确认或业务校验。
- Agent 不得仅根据长期事件宣称订单、库存、退款等当前业务状态。

## 13. 与现有项目的衔接方式

项目已经具备长期事件的基础能力：

- `ai_user_memory_events` 保存用户长期事件。
- Memory Event Extractor 能从被压缩的历史消息中提取事件候选。
- MemoryProvider 能读取近期事件和与当前请求相关的事件。
- ContextBuilder / MemoryMiddleware 能在 Agent 调用前注入动态上下文。
- `search_user_memory` 可以在必要时主动检索更早事件。

新的设计不另建长任务状态表，而是在现有基础上调整职责：

1. 将原有工作流式 `TaskState` 定义退出客服主链路。
2. 继续以 `ai_user_memory_events` 作为长期事件事实来源。
3. 将“近期事件”和“相关事件”的选择统一收敛为 TaskState Selector。
4. 由 TaskState Builder 生成一个去重、有数量限制、因 Agent 而异的 `<task_state>`。
5. 避免同时注入 `<task_state>` 和重复的全量近期事件块。
6. 保留 `search_user_memory`，用于模型确实需要但自动投影未包含的更早历史。

这里的 TaskState 是运行时视图，不需要再维护任务状态机、步骤迁移、执行租约、心跳、崩溃抢占和长任务恢复。

## 14. 推荐实施顺序

### 阶段一：统一语义和准入标准

- 将 TaskState 的项目定义改为“客户长期事件的当前任务投影”。
- 确定事件类型白名单、准入问题和禁止保存内容。
- 明确用户画像、长期事件、会话摘要和实时业务数据的边界。

验收重点：团队面对一条信息时，能够一致判断它应该进入画像、事件、摘要，还是根本不保存。

### 阶段二：完善事件更新链路

- 保留对话异步提取入口。
- 为确定成功且足够重要的工具结果补充事件入口。
- 增加重复判断、纠错、替代、删除和过期规则。
- 确保所有查询只返回当前用户的有效事件。

验收重点：失败工具不会产生成功事件；相同事件不会反复写入；用户纠正后旧事件不再注入。

### 阶段三：实现按任务投影

- 以当前消息、AgentName、业务领域和业务对象构造检索请求。
- 先执行安全硬过滤，再进行相关性排序。
- 每次只生成少量、紧凑的 TaskState。
- 不同 Agent 使用不同可见策略和数量上限。

验收重点：商品问题不会注入无关物流投诉；没有相关事件时不会强行注入；全量历史不会进入 Prompt。

### 阶段四：治理和效果评估

- 观察事件命中率、错误记忆率、用户纠正率和注入后实际使用率。
- 定期清理低价值、过期和重复事件。
- 根据真实客服场景调整类型白名单和 Agent 可见策略。

验收重点不是“记得越多越好”，而是更少、更准、更可解释。

## 15. 是否适合 AI 智能客服

### 15.1 适合的原因

这套方案适合本项目，原因不是客服需要长任务，而是客服需要跨短任务的长期连续性：

- 单次任务保持轻量，不引入不必要的工作流状态机。
- 重要历史可以跨会话复用，提升服务体验。
- 事件与业务实时状态分离，避免历史记忆冒充当前事实。
- 按任务和 Agent 选择性注入，控制成本、噪声和隐私暴露。
- 复用现有长期记忆链路，不重复建设存储和抽取系统。

### 15.2 适用边界

它适合“历史经历会影响当前服务”的场景，不适合以下目标：

- 需要严格推进数小时或数天的自动化工作流。
- 需要保存可恢复的每一步执行现场。
- 需要把长期事件作为订单、支付等业务事实源。
- 试图通过保存所有行为建立无边界的用户画像。

如果未来确实出现长时间运行、可暂停恢复的 Agent 任务，应为它单独设计 WorkflowState 或 RunState，不应再次把两种语义塞回当前 TaskState。

## 16. 面试时如何解释

### 16.1 一分钟版本

> 我最初考虑过用 TaskState 保存 Agent 长任务的步骤和恢复点，但结合智能客服的实际任务分布，发现订单查询、推荐和售后操作基本都是短任务，完整长任务状态机会过度设计。真正缺失的是跨会话的服务连续性。因此我保留 TaskState 这个项目名，把它重新定义为用户长期重要事件面向当前任务的动态投影。底层复用 `ai_user_memory_events` 保存可追溯事件，运行时由 Selector 根据当前问题、Agent 和业务对象只选 3～5 条相关事件，再由 ContextBuilder 注入模型。模型可以提出事件候选，但写入、用户隔离、去重、过期和注入范围都由服务端控制。这样既不会把全量历史塞进 Prompt，也不会把历史事件当作订单等实时业务真相。

### 16.2 高频追问

**为什么还叫 TaskState？**

这是项目内部保留的兼容名称，准确含义是“当前客服任务所需的长期客户状态”，不是行业中常见的长任务执行状态。文档和代码注释必须明确这一点，避免团队误解。

**为什么不直接把所有长期事件放进 Prompt？**

全量注入会增加噪声、成本、隐私暴露和错误关联。事件库负责完整保存，TaskState 负责针对当前任务最小化投影。

**谁决定一条事件能不能保存？**

模型只能生成候选；服务端根据事件类型、证据、重要性、隐私、用户归属和重复情况决定是否写入。

**谁决定一条事件能不能注入？**

TaskState Selector。它先执行用户、状态、过期和 Agent 权限等硬过滤，再根据当前任务进行相关性选择和数量限制。

**为什么用户画像不能替代长期事件？**

画像描述用户当前相对稳定的特征，事件描述带时间和证据的历史事实。画像适合回答“现在偏好什么”，事件适合回答“为什么这次服务要注意某件事”。

**长期事件会不会变成过期事实？**

会，所以事件必须有状态、发生时间、可选过期时间和替代关系。涉及实时业务状态时永远重新查询业务服务。

**模型错误提取怎么办？**

低可信候选不写入；入库事件保留证据引用；用户可以纠正或要求删除；被替代、删除和过期事件不会再进入上下文。

## 17. 最终设计原则

1. TaskState 服务于跨短任务的客户连续性，不服务于长任务恢复。
2. 长期事件保存重要、可追溯、未来仍有服务价值的事实。
3. 模型发现候选，服务端决定写入和注入。
4. 底层事件可以长期保存，进入上下文的内容必须少而相关。
5. 每次注入都先做用户隔离、有效性和 Agent 可见性过滤。
6. 长期事件不能替代实时业务 RPC。
7. 新事实应能纠正旧事实，用户应能要求遗忘。
8. 没有相关事件时不注入，绝不为了“记忆感”制造上下文。
9. 事件质量比事件数量重要，可解释性比模型自由发挥重要。
10. 如果未来出现真正长任务，另建 WorkflowState，不污染当前 TaskState 语义。
