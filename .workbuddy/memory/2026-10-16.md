- 追问：客服 agent 是否用了 AgentLoop。术语澄清+事实回答：
  ①"AgentLoop"是通用概念名（agent 主循环：LLM 调用→工具执行→结果回填→再调 LLM，直到产出最终回复），各家命名不同：OpenAI Agents SDK 叫 AgentLoop、LangGraph 叫 graph executor、Eino ADK 里对应的是 **ReAct RunFunc（buildReActRunFunc）+ TurnLoop** 两层。
  ②本项目事实：**用了，但是框架内置而非自研**——agent.go 的 adk.NewChatModelAgent 创建的 TypedChatModelAgent 内部就是完整 ReAct 循环（chatmodel.go:1097 buildReActRunFunc：模型调用→解析 tool_calls→ToolsNode 并行执行→tool result 回填 state→再调模型，直到无 tool_call 输出最终文本或达 MaxIterations=8）；外层还有 TurnLoop（turn_loop.go）管理多 turn 的调度、checkpoint、中断。
  ③项目自己写的"循环感"代码：consumeEvents（事件消费，不是循环控制）；Supervisor 调子 Agent 也是 tool calling 一轮触发（AgentTool 内部又是一个独立 ReAct 循环）——嵌套循环。
  ④面试口径：用的是框架的 ReAct 循环，两层结构——每个 Agent 一个内层 ReAct（MaxIterations 封顶），Supervisor 的 TurnLoop 做外层编排；没有自研循环控制逻辑，因为 Eino ADK 的循环+checkpoint+中断恢复已经是成熟实现，自研反而要重造这些。
- 追问：项目有没有 harness 工程。术语澄清：harness（测试背带/脚手架）= 让被测系统可被程序化驱动和观测的整套基础设施——Agent 领域 harness 的标准组成：驱动（往 agent 发输入）、环境（业务执行体）、观测（轨迹/事件捕获）、判分（断言）。本项目**有，且是三套 harness**：
  ①evalrunner harness（services/aiagent/cmd/evalrunner + internal/evaluation）：进程内 harness——stdin/stdout JSON 协议驱动（initialize/send/end/confirm），evaluation.State 内存业务环境，轨迹+终态结构化输出；被 Python experiment.py 作为子进程驱动（SimulationClient）。用于快速回归+自进化 A/B。
  ②tau2 适配 harness（eval/tau2-ecommerce/tau2_ecommerce/）：HTTP+SSE harness——agent.py 适配 tau2 HalfDuplexAgent 接口、client.py SSE 解析、simulation/experiment/judge/metrics/scoring 全链路、langfuse_export 观测导出；打真实服务。用于端到端验证。
  ③skill 自进化 harness（cmd/skillevolve + internal/eino/evaluation.go + evolution）：候选注入 trial、A/B 对照、加载证据记录、评测集成——被测对象是 skill 而非 agent。
  关键点：harness 不等于测试用例——它是让"任意 agent 可被驱动、观测、判分"的基建；三套 harness 共享同一判分语义（ecommerce-rules-v1）和任务格式（tasks.json schema）。
- 追问：harness 到底是什么（要本质解释）。给出通俗+本质两层：
  通俗版：harness = "马的挽具"引申——把被测系统"套上车"让它能被程序牵着跑的那套装备。没有 harness，你的 agent 只能人肉打开聊天窗口手敲测试；有 harness，程序能自动发消息、喂环境、收轨迹、打分。
  本质版：harness 是**被测系统与测试用例之间的标准化接口层**——它解决三个"不可测"：①不可驱动（怎么程序化发输入？）②不可观测（内部决策过程怎么捕获？）③不可判定（什么算成功？）。任何系统要被自动化评测，都必须有人造这三个接口，这个"人造接口层"就叫 harness。
  对照具象化：单元测试的 test runner 就是函数的 harness（驱动=调用函数，观测=返回值，判定=assert）；Agent 的 harness 复杂在于：输入是自然语言对话、执行有副作用、成功与否要看数据库终态和行为轨迹——所以 Agent harness 必须包含：模拟用户（驱动）、业务环境（承接副作用）、事件捕获（观测）、终态+轨迹断言（判定）。
  一句话：harness = 让"只能聊天的 demo"变成"可以被 CI 自动化考核的系统"的那层工程。
- 用户自我怀疑"是不是玩具demo"，要求客观评价距企业级差距。给出平衡评价（先纠偏再列差距）：
  【先纠偏——不是玩具】证据：生产级骨架完整（确认状态机+参数冻结+幂等、写操作零重试+三态、Execution Guard 四层防护、checkpoint 中断恢复、熔断降级候选池、全链路审计、评测三套 harness + 30 任务集 + manifest 可复现）——这些是 90% demo 根本没有的东西；"玩具感"来自规模不是架构。
  【真实差距六个维度】：
  1. 规模与压力：单机单实例、无压测数据（QPS/P99/并发会话数）、无水平扩展设计（checkpoint 存 Redis+MySQL 但会话亲和/分布式锁竞态未验证）、内存 checkpoint 用 memoryCheckpointStore 兜底。
  2. 数据与真实流量：fixture 合成数据、无真实用户分布、评测集 30 条是手工设计非生产流量抽样、无在线指标（线上成功率/用户满意度/人工接管率）。
  3. 安全深度：无 prompt 注入的对抗性测试体系、无 PII 合规（GDPR/个保法）数据治理、审计有但无审计响应流程（SIEM 告警）、API key 管理硬编码 config。
  4. 运维可观测：有 Langfuse 但无告警规则（熔断率/超时率/成本突增）、无 SLO/错误预算、无灰度发布机制（skill 自进化有评测但无影子执行/线上灰度——MEMORY.md 已记此缺口）。
  5. 模型与成本治理：无成本预算/配额（按用户/租户）、无模型路由策略（贵模型 vs 便宜模型按任务复杂度）、prompt cache 命中率无监控、无 A/B 上线机制。
  6. 业务纵深：售后退款/物流未接（能力边界声明了）、支付后状态机、库存高并发场景（秒杀）、多租户隔离。
  【定性结论】当前是"架构正确的原型"（architecturally sound prototype），不是玩具——玩具是没有安全边界/评测/降级的；也不是企业级——企业级缺的是规模验证/数据真实性/运维闭环。差距主要在"运行验证"不在"设计"。给了演进优先级排序。
