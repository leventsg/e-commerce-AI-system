- 追问：摘要压缩按 token 怎么压。核对 summary.go MaybeRefresh 完整链路：①触发=双条件（未压缩消息采样累计 token ≥ SummaryTriggerTokens=4000 主条件【HybridEstimator 逐条估 Content 求和，采样上限 30 条】，或条数 ≥30 兜底）；②压多少=水位推进式（不是一刀切）：每轮取最旧 10 条（summaryCompressMessageCount）交摘要模型增量摘要（携带 Previous 摘要），水位=本轮最后一条的 MsgId+CreatedAt 写回 Save；最多 3 轮（maxSummaryRefreshRounds），每轮后未压缩条数-10，直到 ≤20 条保留窗口（summaryRecentMessageCount）或轮数用尽；③摘要本体约束=输出校验（空/超 4000 字/超 12 个 open_tasks 即失败）+TokenCount 记录（模型 usage.CompletionTokens 优先，无 usage 则 HybridEstimator 估 JSON）；④注入时再受 SummaryMaxTokens=2000 clampBlock 截断。注意：压的是"水位之前的原文从上下文消失"，摘要本身是增量滚动合并（Previous→next）。
- 追问：水位存哪。dal/model/ai/conversation_summaries（表 ai_conversation_summaries，go-zero sqlc 带缓存）：水位=covered_until_created_at（已覆盖消息时间水位）+ covered_until_message_id（已覆盖消息ID水位）两字段，作为摘要行的一部分存储（同表字段还有 summary/key_facts/open_tasks/token_count/user_id/conversation_id）；读取=FindLatest 按 user_id+conversation_id 过滤、covered_until 双字段倒序取 limit 1（时间+ID 双水位因 created_at 可能同秒，MsgId 兜底定序）；coveredBySummary 判定=消息时间早于水位时间，或时间相等且 MsgId ≤ 水位 ID。设计要点：水位不是独立表/独立字段，而是"摘要行自带覆盖范围"，插新摘要即推进水位。
- 追问：8.1k→5.6k 口径是"一轮对话"还是"一次 LLM 调用"。给出明确口径：都不是字面义的"一轮"，正确口径是**任务级（task-level）聚合**——一个评测任务从用户首条消息到任务完成（可能 3~12 轮用户对话、内含 1 次任务全程）期间，该 run 内**所有 LLM 调用**（Supervisor 多次 + 各子 Agent ReAct 的每次模型调用）的 prompt_tokens 之和，再对 30 个任务取平均。之所以不能按"一次 LLM 调用"：单次调用口径下压缩组反而可能更高（动态块常驻开销），且一次任务包含几十次调用没有单次可比性；之所以不能按"一轮用户对话"：一轮内也有多次 LLM 调用（路由+子Agent多轮ReAct），轮边界不稳定。分层解释：8.1k=30任务均值（短2.1k/中7.8k/长14.4k），5.6k 对应压缩后（短2.15k/中5.9k/长8.7k）。注意 8.1k 与 TokenBudget.TotalTokens=8000 无关，是巧合接近，被追问时要点明避免混淆。
- 追问挑战："摘要 4000 token 才触发，为什么均值能降 8.1k→5.6k？"关键澄清：**摘要压缩只是四层压缩机制之一，且不是主要贡献者**。四层独立机制：①RecentWindow 滑动窗口（3000 token 封顶，每轮生效）——主要贡献者，长任务全量历史 14.4k 的大头就是无上限的历史原文，滑窗把它钉死在 3k；②水位去重（coveredBySummary，摘要触发后防双份）——次主要，全量组无水位概念、被压缩过的消息原文继续反复重放；③工具结果引用化+按需回捞+块级 clamp（1500/1200/600/600 截断）——工具多轮任务的大头，cart_list 这类结果一次 1-2k token，全量组每个历史调用结果都重放；④摘要本身（4000 触发/2000 注入）——只是"滑窗溢出部分的信息保全"，替代性机制不是省 token 主力。回答要点：对照组（DisableCompression）四层全关才叫全量注入；单层触发阈值高 ≠ 整体收益小；A/B 差异来自四层叠加。数字自洽性：长任务 14.4k→8.7k，其中滑窗省~3k、水位去重省~1.5k、工具引用省~2.2k（示意分解）。
- 用户纠错（正确）：恢复不是"重新组装上下文再调模型"。核对 turn_loop.go + memory_middleware.go 确认：①恢复从 checkpoint 的 resumeBytes 定点恢复图执行，中断点之前的消息状态从 checkpoint 反序列化，不重新走 Retrieve 组装——历史 token 不重复计费；②但恢复后若继续 ReAct（工具执行完→下一步仍需模型决策），BeforeModelRewriteState 会在恢复的模型调用前再次触发，不过本项目 middleware 有 memoryPreparedContextKey 按 agent 去重防重复组装，且状态里的消息来自 checkpoint 不是重新查询；③真正会重复计量的边界情况：任务失败整体重跑（新 run 新 checkpoint，一切重新计）和摘要水位推进后同 run 后续调用注入更精简的历史（这是变化不是重复）。之前"恢复 run 重复计数"的说法不准确，评测去重按 checkpoint_id 的理由应修正为：防的是"同任务重试/重跑"而非"resume 双计"。resume 语义 = 定点续跑，不是重新开始。
- 追问确认：上下文组装位置=memory_middleware.go 的 BeforeModelRewriteState（adk.ChatModelAgentMiddleware 钩子），每次模型调用前触发；组装动作=调 MemoryProvider.Retrieve 拿三段（SystemMessages/HistoryMessages/ContextMessages），重写 state.Messages（system 原样保留+SystemMessages+History+运行时块追加到最新 user 消息）；middleware 有 memoryPreparedContextKey 防同 run 重复组装。注意区分：组装在 middleware、数据在 Provider、决策（压缩/滑窗）在 Retrieve 入口——三层职责。
