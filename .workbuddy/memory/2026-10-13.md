- 追问：为什么用 HybridEstimator 而不用模型返回的 usage.PromptTokens（后者才是真实值）。核心论证：**用途决定口径**——两者服务不同目的，不可互换：
  ①真实 usage 是**事后值**（响应返回后才知道），而所有预算决策（滑窗裁剪、块截断、摘要触发）必须发生在**发送前**——不可能用还没拿到的数做裁剪。这是因果时序，不是精度问题。
  ②真实 usage 是**模型相关**的（不同 tokenizer/模型数值不同），做预算标准会把系统绑死在特定模型上；估算器模型无关，换模型预算体系不动。
  ③真实 usage 是**整段值**（一次调用一个总数），无法归因到"哪条消息多少 token"——滑窗需要逐条扣减（每条消息一个 cost），总数没法做增量裁剪决策。
  ④性能：预算检查每条消息/每块都要算，调 LLM 或调 tokenizer API 不现实；HybridEstimator 纯 CPU 遍历 O(n)。
  ⑤偏高的方向性正确：中文 1:1 vs 实际 0.6-0.8 偏高估 → 宁可少放消息也不会超窗，配合 SafetyFactor 0.9 双保险。
  真实 usage 的正确用途：事后校准（用实测/估算比值回归修正估算器参数）+ 成本核算 + Langfuse 观测（summary_model.go 已读 PromptTokens 用于摘要记账）。评测口径用真实 usage（之前 A/B 设计已明确），决策口径用估算——两套各司其职。
- 快问快答：英文预估比例。HybridEstimator：ASCII 4 字符 ≈ 1 token（domain/token.go `(ascii+3)/4`，即向上取整）；"other"类（拉丁扩展/符号）2 字符 ≈ 1 token；CJK 1 字 ≈ 1 token。4:1 依据是 GPT 系/BPE 经验值（英文单词平均 ~4 字符、1 token ≈ 0.75 个英文单词）。
- 追问：摘要压缩压的是什么、压完是否必然低于阈值。①压的内容=未压缩的对话流（user/assistant 原文消息，最旧 10 条一批，经摘要模型转成 {summary,key_facts,open_tasks} 结构化摘要，水位推进），只动对话流——system prompt/稳定前缀（画像+事件）/工具引用/task_state/RAG 各块有独立 clamp 预算，不参与摘要压缩。②不保证单次压完达标：单次最多 3 轮×10 条，极端 backlog（如历史 100+ 条）压不完留到下一轮调用继续；③更关键的边界：token 阈值（4000）是【摘要触发阈值】不是【总上下文上限】——即使对话流压到很小，上下文总量 = system+稳定前缀+摘要(≤2000)+滑窗(≤3000)+各块(1500+1200+600+600)+当前消息，理论上可超 4000/8000——因为设计不做"总token硬顶裁剪"（文档§8：不因估算超预算拒绝调用），预算是逐层 cap 控制+偏保守估算，TotalTokens×0.9 仅观测参考。防失控兜底：各层独立 cap 后总量有界（≈8-9k 量级），且 SafetyFactor+偏高估算让真实值低于估算。
- 追问：为什么触发条件要加条数 30 兜底而非纯 token。核对 summary.go 注释"防估算偏差导致 backlog 失控"+双条件 `sampleTokens < X && count < 30 则不压`（或语义）。深层理由四条：①估算器有系统性偏差风险（中文偏高估安全，但极短消息/表情/符号流可能偏低估——如"嗯""好"这种 1 字消息估 1 token 但加消息框架开销 chat template 每条还有固定 overhead 估算器完全没算）；②消息框架 overhead：每条消息在 chat template 里有 role 标记/分隔符等固定 token 成本，HybridEstimator 只算 Content 不算框架——短消息会话实际 token 增长远快于估算，纯 token 触发会延迟触发；③条数兜底防"慢性泄漏"：万一出现估算长期低于实际的场景，未压缩消息无限堆积，30 条强制触发切断了尾部风险；④运维简单性：条数是精确可数的（COUNT 查询），token 是估算值——用精确的数做兜底、用估算的数做主判断，两层互补。语义：token OR 条数，任一满足即压（防漏）；而不是 AND（防过度压缩）——方向是宁可早压不可晚压。
- 追问：双触发设计是否合理 + 主流做法对比。判定：合理且对齐主流（token 主判+条数兜底是业界标准防御组合）。主流参照：①LangChain ConversationSummaryBufferMemory：max_token_limit 主判（用 len 或简单 tokenizer 估）+ 结构上按条维护；②Mem0/Letta(MemGPT) 分层记忆：按条数/分值管理工作记忆，页替换式；③Claude Code：上下文接近 92-95% 窗口时自动 compact（按已用量/窗口比），配合 /compact 手动；④OpenAI Assistants（旧）file/turn 截断按条 truncation_strategy（last 20 messages 或 steps）；⑤Agno/app-builder 类多为 turns 数。共识：token 比例更贴真实，条数更稳，生产系统普遍双保险。本项目差异点：阈值是绝对值（4000）而非窗口比例（92%）——换模型窗口变化时要重配；可改进项：a) 改为窗口百分比制（自适应模型窗口）b) 把消息框架 overhead 计入估算器（每条+N 常数）c) 用真实 usage 校准估算器斜率。诚实评价：当前设计在"正确性>精巧"维度合格，未做比例制是已知取舍。
- 追问：按条数压缩会不会截断一个 turn（一问一答对被拆开）。核对：压缩单位=消息条（10 条/批），确实可能把一问一答拆到两侧（问在摘要、答在滑窗）。三层缓解+残余风险：①摘要模型输入是连续消息序列（不孤立），语义整体性在摘要里保留；②结构化摘要带 key_facts/open_tasks，关键信息显式留存；③ReAct 内部轮（当前 run 进行中的消息）不参与压缩——CompressIfNeeded 压的是数据库里已落盘的历史消息，当前 turn 的消息还在生成中或已由 ADK state 管理，不会被中途抽走。残余风险真实存在：turn 边界切割可能造成"答在滑窗问在摘要"的弱连贯，但影响是语义性的不是结构性的（不会产生孤儿消息）。可改进：按 turn 对齐压缩（成对切分，user+assistant 原子单位）——业界 MemGPT 也按条不按 turn，Claude Code compact 是整体重写无此问题。诚实定性：已知次优，影响低（摘要保留语义+水位只影响注入不影响完整性），按 turn 对齐是 backlog 项。
- 追问：摘要压缩本身出错怎么办。核对 failure path：①摘要模型调用失败/输出解析失败（空/超4000字/open_tasks>12）/Save 失败 → MaybeRefresh 返回 err → CompressIfNeeded 返回 err → ContextBuilder.RefreshVolatile 记 metadata["context_compress_degraded"] 继续（不中断不重试）→ 下一轮调用再试；②关键安全性质：**原始消息永不删除**——ai_messages 是事实源，压缩只是"水位推进+新摘要行"，水位不推进=下轮重新尝试压缩同一批，天然幂等重试；③摘要错误的危害边界：不会丢数据（原文都在）、不会阻塞对话（降级继续）、最坏影响=该轮上下文略大（滑窗仍然生效兜底 3000）；④坏摘要已落库的场景：Save 成功但内容质量差（幻觉/丢关键事实）→ 水位已推进，该批原文退出注入——这是真实风险，防线：输出硬校验（结构合法性）+key_facts 结构化比对+人工/评测抽查；可改进：摘要后校验轮（摘要与原文的关键实体比对）。⑤上游连锁：onCompressed 异步发布（WithoutCancel）失败不影响主链路。
- 追问：为什么 Tool Result 是上下文主要成本。四条结构性原因：①**只增不减的累积性**——对话消息一问一答是抵消结构（user 短 prompt、assistant 总结后也短），而工具结果是单向堆积：每个多轮任务产生 5-15 次工具调用，每次结果 0.5-2k token（商品列表/订单详情都是结构化大 JSON），且一旦进上下文就每轮重放；②**膨胀系数**——工具结果为机器可判设计的结构化 JSON（envelope+字段+数组），比自然语言啰嗦 3-5 倍：同信息量"找到 3 件商品"一句话 vs products 数组带全字段 1.5k token；③**ReAct 放大器**——子 Agent 每轮 ReAct 都把之前所有工具结果重放一遍（模型需要完整轨迹决策下一步），多轮任务里第 N 轮的输入包含 N-1 轮全部结果——O(n²) 增长；④**信息利用率低**——结果里大部分字段（picture/sold/categories）模型用一次就不再需要，但一直占位。这解释了为什么四层压缩里"工具引用化+回捞"贡献大：把"常驻全量"改成"常驻引用+按需全量"，直击累积性和利用率两点。量化参照：cart_list 一次 1-2k、product_search 0.5-1.5k、order 详情 1k+，长任务 10+ 次调用若全量重放就是 8-15k，超过对话文本本身。

- 快问快答：event_id=ai_user_memory_events 表的主键 id（newUserMemoryEventID 生成，UUID 类），一行长期记忆事件的全局唯一标识。作用：①向量库 upsert 的幂等键（同一事件重提 embedding 覆盖旧向量不产生重复）②删除/状态翻转（status active→deleted）的定位键 ③溯源锚点（关联 source_message_ids）④MySQL 事实源与向量派生索引之间的对账键。注意：模型不可见不可传（检索按 user_id 硬过滤，event_id 只在系统内部流转）。
- 追问：每次 LLM 生成事件都是新 event_id，为何还要幂等。澄清：幂等要求的不是"event_id 相同"，而是"同一业务事件不被重复入库/入索引"。三个真实重复来源：①Kafka 至少一次投递——消费 AiMemoryUpdates 消费者 crash/rebalance 会重投同一条消息，Extractor 重跑提取出同样的事件（新 event_id 但同一事实）→ 同一事实两行/两个向量，检索时重复霸占 top-k；②提取器重试——批次失败重跑整个 batch，前半已入库的再入一次；③向量库写入重试——embedding 后 upsert 网络超时重发。幂等键选择分层：写向量库用 event_id 幂等（同 id upsert 覆盖——解决③）；提取层防①②靠 dedupe（如 source_message_ids+type+event_date 业务去重键或库级唯一索引），不是靠 event_id——event_id 只能防"同一行写两次"，防不了"同一事实生成两行"。承认现状：SaveUserMemoryEvents 当前是纯 INSERT 无去重索引，①②的重投场景靠 Kafka 消费偏移量管理兜底，严格幂等是 backlog。
- 追问：Eino Langfuse callback 能否采集中断事件。核对 eino-ext/callbacks/langfuse/v2@v2.0.2 源码——**能，v2.0.2 原生支持**：①识别三通道（interruptionCause）：compose.IsInterruptRerunError / compose.ExtractInterruptInfo / adk.InterruptError（errors.As）——graph 中断、tool StatefulInterrupt 冒泡、ADK 业务中断全覆盖；②上报形态：observation status="interrupted"、output={"status":"interrupted","cause":...}（JSON）、metadata.eino_callback_interrupted=true + eino_interrupt_cause、level 不置 ERROR（与真错误区分）、status_message="operation: interrupted"；③traceRun.recordInterruption 记 run 级中断结论；④与取消区分：先判 cancellation 再判 interrupted，两个独立 outcome。本项目高风险确认（StatefulInterrupt→CompositeInterrupt→ADK InterruptError）会走 adk.InterruptError 通道被捕获；注意点：cause 是 err.Error() 原文（含 InterruptContexts 信息量有限——confirmation_id 不在其中，需本项目自己补：已有 interruptEventToDomainEvent 转 confirmation_required 事件+BindResumeTarget 落 confirmations 表，业务侧证据比 callback 全）。

- 追问：手动埋点把 confirmation_id/参数挂 span，spanID 怎么获取。核对项目 observability 包（OTel 标准做法，已完全解决）：
  ①核心机制：**不需要手动找 spanID**——OTel 语义是 span 藏在 ctx 里，trace.SpanFromContext(ctx) 取当前活跃 span，SetAttributes 直接挂属性，spanID 由 provider 内部管理。项目三种姿势：
  a) obs.Event(ctx, "confirmation.created", status, fields)——瞬间事件（approval.go 里 confirmation 创建就是用这个？实际用的 logx+Event 混合）：内部 Start+立即 end，fields 全部变 metadata 属性；
  b) obs.Start(ctx, name, fields) 返回 end 回调——持续 span；
  c) 已有 span 上追加：trace.SpanFromContext(ctx).SetAttributes(...)（Result 函数就是这个写法）。
  ②挂 confirmation_id 的正确位置：高风险确认的两个时机——approval.go createApprovalInfo 成功后（ctx 此刻在 tool 调用链内，SpanFromContext 拿到的就是该工具的 span）挂 confirmation_id/tool/参数摘要；ResumeStream 批准/拒绝时同样 Event。字段名用 langfuse.observation.metadata.confirmation_id（Langfuse metadata 约定前缀）。

  ④跨边界（Resume 是新请求新 ctx）：confirmation_id 通过 Correlate 挂 trace metadata，新 trace 里 Correlate 同一个 confirmation_id 即可串联两次 trace。

- 追问：8.1k→5.6k 哪个优化贡献最大。回答：滑动窗口（RecentWindowTokens=3000）是最大单一贡献者（估长任务 ~3k/任务，占总降幅 2.5k 的 ~45-50%）——理由：它是唯一"每轮无条件生效"的机制（摘要要触发、引用化要有多轮历史才有得省），且对照组的历史重放正是长任务 14.4k 的最大构成。第二梯队：工具结果引用化+回捞（~2k，作用于工具密集任务）；水位去重（~1.5k，与摘要是同一机制的两面）。摘要本身（2000 注入）贡献最小——它是滑窗的信息保全配套不是省钱主力。方法论强调：贡献归因不能拍脑袋，正确做法是消融实验（ablation）——四机制逐个关闭跑四组，各分量单独测；或看 per-layer 分层数据（短任务无差/中任务工具引用生效/长任务全生效）反推。面试口径：先给直觉排序+归因逻辑，再补"严格结论需消融"。
