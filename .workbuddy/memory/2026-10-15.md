- 追问：熔断器依附在哪/谁有/是否互相影响。核对 resilient_factory.go + model.go + breaker.go：
  ①依附位置：熔断器是 CircuitBreaker 独立对象，通过 resilience.Candidate.Breaker 字段绑定到候选模型上（每个候选一个 breaker 引用）；物理存储=resilientModelFactory.breakers 是 sync.Map（modelIdentity→*CircuitBreaker），工厂持有。
  ②谁有熔断器：候选池里每个模型候选（主模型+备用模型）各一个，但**按 modelIdentity 共享**——key=Provider+BaseURL+Model+APIKey 四元组；supervisor 和每个子 agent 各自调 NewChatModel，同一模型（四元组相同）复用同一个 CircuitBreaker，共享健康状态。即"每个模型一个熔断器"而非"每个 agent 一个"。
  ③是否互相影响：模型之间**不互相影响**（各自独立状态机、独立计数、独立冷却）——主模型熔断不影响备用模型状态；但**同一模型的多个使用方（supervisor+所有子agent）共享同一个熔断器**，会互相影响（一个 agent 把主模型打熔断，其他 agent 也立即走备用）——这是刻意设计（共享健康状态，避免重复探测），但要能讲清边界。
  ④特殊：NewStructuredChatModel 不接候选池（结构化输出模型保持单模型）；候选构建失败是配置错误启动即失败不静默降级；WithTools 共享熔断器（重建候选但 breaker 复用）。
  ⑤懒半开探针+并发安全：breaker 用 atomic 操作，Allow 的 CAS 保证半开探针并发安全。
- 追问：switchingStreamReader 怎么判断"首个有内容字节已发前端"。核对 model.go pump() + hasCommittedContent()：
  机制：pump goroutine 逐 chunk 从底层候选流读出 → 立即 writer.Send 写给上层（上层=Eino事件流→最终SSE前端）→ 本地布尔 committed 初始 false；每读到一个 chunk 先用 hasCommittedContent 判断，true 则置 committed=true。此后再出错就走"已提交"分支（透传错误不换候选）。
  hasCommittedContent 判定四条件（任一满足即"有内容"）：msg.Content != ""（正文文本）、len(msg.ToolCalls)>0（工具调用）、msg.ReasoningContent != ""（思考内容）、msg.Extra["reasoning-content"] 非空（部分 provider 把思考放 Extra）。
  关键细节：①空 chunk 不算提交点——"一堆空 chunk 后断流"仍可安全换候选（空 chunk 本身没发给用户任何可见内容，上层也会跳过）；②判断的是"从底层模型流读到的 chunk"，Send 之后即视为已向前端提交（pipe 直通，中间不再撤回）；③committed 是本地变量非跨协程状态——pump 单协程读写无竞争；④判断粒度是 chunk 级不是字节级——凡带任何可见内容（文字/工具调用/思考）的第一个 chunk 就是提交点。
