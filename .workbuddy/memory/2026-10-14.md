- 追问：Langfuse callback 是否自动追踪中间件执行。结论：**不会自动追踪自定义中间件的内部逻辑**。机制核对：langfuse v2.0.2 是 eino callbacks.Handler（OnStart/OnEnd/OnError/流式四钩子）——它的触发点挂在 eino 的标准组件边界：模型调用（chatmodel wrapper 第 7 层 callbackInjection）、工具调用（callbackInjectedToolCall）、图节点——这些边界自动触发。但 ChatModelAgentMiddleware（记忆/审批/skill 中间件）是业务代码，运行在组件边界"之内"：BeforeModelRewriteState 在模型调用前执行但 callback 只在真正调模型时 OnStart——中间件内部的取数、压缩、判断逻辑不在任何 callback 触发点上。证据：本项目 memory_middleware.go/approval.go 内部没有 callbacks. 调用。要追踪中间件内部的两种方式：a) 中间件内部自己用 OTel（项目现状：obs.Start("context.assemble")——自己开 span，与 callback 同 TracerProvider 自然同树，Langfuse 能看到但属于业务埋点不是 callback 自动追踪）；b) eino 的 callback 只覆盖标准组件边界，中间件想被追踪必须自己发。注意区分：ADK 源码注释里 "callbacks" 指其内部 handler 机制（AgentMiddleware 也有 callback 钩子形态），但 Langfuse handler 消费的是 OnStart/OnEnd 生命周期事件——中间件作为 handler 挂载≠中间件内部被观测。
- 追问：skill 的 backend 是什么。回答：skill.Backend 是 Eino skill 中间件定义的接口（List(ctx)→[]FrontMatter 索引 + Get(ctx,name)→Skill 正文），即"skill 的存储后端抽象"——中间件不关心 skill 从哪来，只通过这个接口取。两种实现：①官方 filesystem backend（NewBackendFromFilesystem）：扫描 BaseDir 下一级子目录的 <dir>/SKILL.md，frontmatter（name/description/context/agent/model）+ markdown 正文；②本项目自研 skillBackend（skills.go）：适配内嵌 skills.Document（go:embed 进二进制的 SKILL.md 文本），List 返回 name+description，Get 按 name 返回正文并回调 onGet(name,hash) 记录真实加载证据（评测 A/B 用）；另支持 SkillSet 外置覆盖（Documents map 覆盖内嵌同名）——自进化候选 trial 注入就是走这条路。设计意义：接口隔离"加载机制"变化（内嵌→文件系统→远端），中间件/评测逻辑不变。与 MEMORY.md 长期笔记"Skill 配置化加载"方向呼应：外置目录扫描即 filesystem_backend。
- 追问：模型第一次说要退款（泛化到高风险操作），用户确认后怎么保证执行的还是同一笔。四道机制（核对 approval.go + confirmation/manager.go）：
  ①参数冻结：StatefulInterrupt(ctx, info, argumentsInJSON) 把当时参数存进 interrupt state（checkpoint 持久化）；Resume 时 GetInterruptState 取回 storedArgs，批准后 endpoint(ctx, storedArgs) 执行的就是冻结参数——不是恢复后让模型重新生成参数。resume 路径新参数即使被篡改也不使用。
  ②确认行快照：RequestConfirmation 落 ai_confirmations（status=pending，含 tool_name + arguments JSON + summary + TTL + run_id/checkpoint_id），用户看到的确认卡片渲染的就是这行——所见即所冻。
  ③状态机一次性：Decide 用分布式锁 withLock + status==pending 才能转移（approved/rejected），MarkExecuted 再转移 executed；非 pending 直接 ErrConfirmationAlreadyProcessed/状态错误——同一 confirmation_id 只能走完一次 approve→execute。
  ④跨用户/过期：loadOwned(user_id+conversation_id+confirmation_id) 校验归属；过期自动转 expired。
  边界说明：本项目无退款工具（能力边界声明），同机制适用于 order_cancel/cart_delete 等真实高风险工具；若模型恢复后"想改参数"，ADK 恢复语义是定点续跑 storedArgs，不存在重新生成空间。
- 追问：Resume 后底层数据变了（中断时库存 1、恢复时 0）怎么办。分层答案：
  ①首先——参数不重生成（上一问的机制不变）：恢复执行的仍是冻结参数（product_id=42, quantity=1），数据变化不影响"执行同一笔"的保证——变的不是操作，是世界的状态。
  ②执行时点的真实校验（核心答案）：冻结的只是"意图+参数"，不冻结"前提条件"。业务 RPC 在执行时点做真实校验——库存服务收到扣减请求时库存为 0 → 返回业务错误（库存不足）→ 工具走失败路径：classifyToolError 判为 permanent（业务拒绝），不重试、envelope status=failed、business_outcome=not_executed（未扣任何东西）→ 模型看到失败结果向用户说明。**不可能出现按旧库存成功扣减的超卖**：库存扣减是服务端原子操作（UPDATE ... WHERE stock>=1 或等价），上下文里的"库存1"只是快照信息，真实扣减看数据库当前值。
  ③时序语义：冻结参数=意图不可变；数据时效=执行时校验。类比"下单时冻结价格但支付看余额"。
  ④提示层配合：checkout_prepare 的 unknown 处理、prompt"写操作前重新核实"——但机制兜底不依赖 prompt。
  ⑤若失败后用户还想要：新一轮交互重新走完整链路（重新查库存、可选替代品、重新确认），旧确认已 executed/failed 终态。
  关键点：参数冻结管"同一性"，执行时校验管"有效性"，两层正交——前者防调包，后者防过期前提。

- 追问：Tool Call 参数值错误（schema 对但值不对）怎么办。分两类答：
  ①格式/范围错（product_id=0、quantity=-1、类型对但超界）→ Execution Guard 强类型校验（helper.RequiredInt64Argument/PositiveUint32/AuthenticatedUserID32/QueryPagination 上限）→ invalid_arguments permanent 拒绝，不发 RPC，envelope 带 error.code+指向性 safe message（"工具参数不正确，请根据错误信息调整后重试"）→ 模型下一轮针对性修正。
  ②语义错（值合法但业务不对：商品不存在、库存不足、券过期）→ RPC 返回业务错误 → classifyToolError bizerr.Parse → permanent（业务拒绝），SafeMessage 用业务真实消息（"库存不足"），不重试 → 模型如实转述用户。
  ③值错误的源头防御（预防>纠错）：schema Desc 写单位（分）枚举来源（from coupon_list）；prompt"使用真实 ID 不编造、缺参只追问"；参数期望来自工具结果引用（$ref）而非模型凭空；写操作前重新 RPC 核实动态值。
  ④关键边界：permanent 错误永不自动重试（区分 transient），且失败不被总结为成功（business_outcome 三态）；值错误消耗一轮 ReAct 迭代但不吃写重试预算。
- 追问：LLM API 超时怎么办。核实：项目当前**未启用** Eino 的 retry_chatmodel / failover_chatmodel（model_factory.go 只配 openai.ChatModelConfig.Timeout，config/config.go 有 Timeout 字段，无 Retry/Failover 配置项），但框架能力齐备：
  ①超时→模型调用报错→consumeEvents 捕获 event.Err→businessExecuted 分支：未执行→发"AI 服务暂时不可用，请稍后重试"；已执行业务→"业务结果已产生，但模型总结失败，请勿重复操作"（business_executed=true）→返回 done，不假装成功。
  ②框架级可加（未用，属演进项）：Eino adk retry_chatmodel（ErrExceedMaxRetries/RetryExhaustedError 包装最后错误、WillRetryError 事件实时观测重试）+ failover_chatmodel（多模型链：超时/不可用时 GetNext 切换下一模型，failoverCurrentModelKey 记录当前）；retry 适合瞬时抖动，failover 适合服务不可用/限流。
  ③业务语义防线：模型不可用≠业务失败——已执行的写操作结果保留（business_executed 标记），不因总结失败而否定业务结果；"模型不可用时明确提示稍后重试，不编造业务结果"（prompt 铁律）。
  ④超时配置本身：openai ChatModelConfig.Timeout（config 注入，秒），超时由底层 http client 触发 context.DeadlineExceeded。
  面试口径：当前策略=超时→不重试直接降级提示（宁可失败清晰不可无限等待）+ 框架已备 retry/failover 能力留作演进；已执行写操作不因模型超时被吞。
- 追问：超时如何改进优化 + 主流 agent 怎么做。核实：规则兜底 Planner 在 implementation-plan 里是 Step 3 的待办项（未实现，计划含 fast LLM 优先→一次重试→规则兜底）；项目当前无 retry/failover 启用。给出优化分层（对齐主流 OpenAI Agents SDK/Claude Code/Anthropic 实践）：
  ①重试层：只重试幂等瞬时错误（429 限流/5xx/网络超时/context deadline），指数退避+全抖动 jitter+上限；429 必读 Retry-After header；区分"首 token 前超时可安全重试 vs 流式中途超时重试代价高"。
  ②failover 层：多模型/多 provider 链（主 deepseek→备 qwen），按错误类型路由（超时/不可用→切下一模型，Eino failover_chatmodel 现成）。
  ③熔断层：连续 N 次失败或错误率超阈值→熔断短路一段时间（防雪崩、给上游喘息），半开探测恢复。
  ④超时分级：TTFT（首 token 超时，短，快速失败重试）vs 总超时 vs 流式 idle 超时（长时间无 token 断开）三分离——单一 Timeout 是最粗的配置。
  ⑤业务降级（本项目特色落点）：模型不可用→规则兜底 Planner（意图识别+参数抽取+缺参追问，走同一 Tool Registry 和 Execution Guard），只覆盖明确中文意图（查单/加购/领券/取消/下单），兜不住的就"稍后重试"。
  ⑥语义缓存：相同 prompt 前缀命中缓存（prompt cache 已有）+ 语义相似查询复用，降调用次数源头减超时概率。
  主流对照：Anthropic 官方建议 429 尊重 Retry-After + 指数退避 jitter；OpenAI Agents SDK 内置 max_retries+timeout；Claude Code 多模型 failover+自动降级；LangChain with_retry + fallbacks 链。
  优先级排序：TTFT 分级+重试（性价比最高）> 429 Retry-After 感知 > failover > 熔断 > 规则 Planner（工程量最大收益明确但只兜窄意图）。
- 模型稳定性方案设计（用户主导构思+我补充完善）。用户方案要点：每模型独立熔断器、主备模型候选池按优先级排序、懒探针（请求来才判断是否需探针，非定时）、30s cooldown 半开、全不可用返回"模型暂不可用"、超时按状态码分可重试/不可重试、重试3次才熔断、流式中断/工具结果返回时模型不可用两个特殊场景。
  我的补充三个关键缺口：①熔断阈值从"连续3次"升级为"滑动窗口错误率"（10s 窗口 >50%），防偶发误熔断；②懒探针细节：Open 且距上次打开>cooldown 时，用真实请求做 probe（省独立健康检查端点），probe 失败不重试直接走下一候选；③状态码分类表：429(读Retry-After)/408/5xx/网络超时=可重试；400/401/402/403/422=不可重试直接熔断（配置凭证问题重试无意义）。
  两个特殊场景落点：a)流式中途失败（部分token已发）→不重试（重试会重新生成导致重复/不一致），标记失败提示用户重发，因为本项目是 SSE 逐token直出；b)工具结果返回时模型不可用→复用已有 business_executed 机制：业务已执行就不重试总结，明确告知"结果已产生请勿重复操作"，防重复下单。

- 模型稳定性与降级方案（本轮定稿，产出 docs/model-resilience-design.md，纯设计未动代码）。用户三个关键决策已拍板：①熔断阈值=「连续失败请求达阈值」（单请求内重试3次算1次失败，连续N个失败请求才熔断，N默认3，容忍瞬时抖动防flapping）；②流式降级=「完整版」：Stream 首个有内容字节前断流也能换候选（switchingStreamReader 追踪 committed 提交点，未提交则换下一候选从头重流同一份 messages）；③全熔断=直接报错不接规则兜底 Planner。
  核心设计（面试可引用）：熔断三态 Closed/Open/HalfOpen + 懒半开探针（不设后台定时器，请求来时判断冷却是否到期才放行1个探针，省资源省调用成本）；候选池按优先级降级；重试边界必须画在「模型层」而非 agent 层——同一份 messages 重试不重跑 ToolsNode（直接解决「工具结果返回时模型挂」不重复下单）；提交点定义=第一个有内容chunk（Content/ToolCalls/reasoning 非空）；不可重试状态码分两类：401/403（鉴权配置，等探针不愈、需告警）vs 400/422（我方bug，需修码）；熔断器按模型身份(provider+baseURL+model+apiKey hash)共享，supervisor+5子agent共用同一健康状态，进程内 sync.Map 即可（多副本独立熔断最终一致够用）。
  重试分类表：可重试=429(读Retry-After)/408/500/502/503/504/网络超时/context deadline；不可重试=400/401/403/404/413/422。落地顺序：resilience包(熔断器+Classify)→ResilientModel.Generate(先覆盖summary/profile无副作用模型)→Stream+switchingStreamReader→ModelPoolConfig(向后兼容单Eino)→前端错误码→可观测埋点+全熔断告警。
